# 从仓库建立解释，再用证据修正它

这里提供可组合的方法，不规定每篇按相同步骤、次数或章节展开。

## 首次认识项目

先确认用户想理解什么。结合 README、包与构建清单、程序入口、配置、核心目录、设计文档和测试，分辨真实运行系统与示例、测试夹具、生成代码、第三方依赖。目录只用于定位，按实际职责解释组件：谁接收用户请求、谁保存状态、谁执行工作、谁提供接口、谁负责外部交互。

系统介绍应让读者知道“它能做什么、为何需要这些部分、各部分如何连起来”。一个命令、请求、用户操作、任务或数据处理过程通常能把架构与实现串起来。依照真实项目选择代表路径：库可以从公开 API 跟到算法和数据结构，桌面应用可以跨界面、进程桥与后台服务，基础设施可以追到控制决策和实际执行面。复杂单体、单文件库和多仓库系统不必使用同一张架构图。

不要用技术栈名单代替架构。说明框架或关键依赖在这里实际负责什么、状态在哪里、哪些组件同进程、哪些边界跨网络或持久化，以及这些选择带来的约束。很大的仓库不需要逐文件扫描正文；从完整结构找入口，再围绕能证明系统模型的路径深入，明确尚未跟踪的区域。

## 自主选择后续问题

阅读历史的研究问题、结论与范围，辨别哪些机制已经解释、哪些只是被提到、哪些在当前代码中值得重新核验。可以从用户目标、复杂度集中处、跨边界协作、状态转换、扩展机制、算法、工程取舍或相互矛盾的证据寻找问题。

让问题足够具体，例如“任务被中断后，谁决定继续还是重新执行，哪些状态保证结果不会重复提交”。这比“分析任务模块”更能驱动阅读；不同项目应提出不同的问题，不必固定围绕任务、队列或 Agent。

历史不限制探索自由。源码可以推翻过去的模型；某个深入问题可能需要重画局部架构、跨越原有分类或重新核验首篇中的关系。说明新发现怎样改变认识即可，不必重复整篇总览。首篇中的建议只是线索，不是待办清单。

## 追踪与反证

定位实际入口及注册位置，沿调用关系追踪参数、数据结构、状态所有权、转换、外部副作用和结果消费方。对重要跳转找到连接依据：函数调用、配置绑定、事件订阅、路由注册、队列生产与消费、插件装配或跨进程协议。接口存在不表示实际被调用，名字相近不表示数据贯通。

按问题检查会影响机制的错误与边界。只读成功分支不足以解释重试；只读锁的声明不足以解释并发；只读测试名称不足以证明覆盖了真实实现。将生产路径与测试断言、文档意图、配置分支互相对照，留意同名但未使用的实现。

建立暂时解释后，主动寻找能推翻它的例子：其他调用方是否绕过该路径，另一种配置是否选择不同实现，错误分支是否留下部分状态，测试是否表达不同契约。无需把所有边界都变成报告章节；只展开会改变读者判断的内容。

## 什么时候已经足够

当研究问题得到有来源的回答、关键连接和约束讲得通，且继续探索不太会改变核心结论时，可以交付。证据不足时继续定位或缩小问题，明确不能确认的部分。不要把“读了很多文件”当成完成标准，也不要把结构性推断描述成已经观察到的运行行为。
