# 源码证据与研报交付

## 让结论能回到实现

关键结论附近给出本次 Commit 的 GitHub 链接，例如 `[执行入口](https://github.com/owner/repo/blob/完整SHA/src/core.ts#L20-L45)`，同时解释对应符号做了什么。引用应支持附近的具体说法，而不是一段讨论后挂一组无说明的文件链接。

调用关系要有连接处，数据流要有输入、转换与消费方，状态约束要有写入和读取位置。测试可以证明断言的意图；没有运行它时写“测试覆盖了这个预期”，而不是“实测通过”。没有直接设计依据时，使用“从实现推断”等清楚的措辞，不替作者编造动机。

从 README 获得的用途说明可以作为起点，整体架构和关键执行路径仍须回到源码。外部资料中的版本、场景或假设与本次代码不一致时，说明差异，不拼成一个虚构实现。

## 机器可核验的证据文件

`output/evidence.json` 的格式由实际 Prompt 决定，基本内容如下：

```json
{
  "complete": true,
  "commit": "本次完整 Commit SHA",
  "questions": ["本篇实际回答的问题"],
  "citations": [
    {
      "claim": "被源码支持的核心结论",
      "file": "仓库相对路径",
      "start_line": 20,
      "end_line": 22,
      "quote": "这些行的完整源码原文，逐字保留"
    }
  ]
}
```

文件和行号必须来自本次跟踪源码，正文中也使用这些引用。至少需要支持核心实现的源码，不能只有文档或测试。可以用短小的只读辅助代码提取原始行，避免手工复制转义时出错；不要为通过校验篡改源码或证据原文。

`complete=true` 表示关键问题已有足够证据，不表示读完整个仓库、运行了所有测试或证明系统完全正确。关键环节仍无法核实时使用 `complete=false` 并在报告说明原因，不能靠图表或常识补齐。

## 写作与图形

先让读者知道问题和总体过程，再解释需要深入的结构、分支与取舍。术语出现时解释用途，必要代码片段围绕论证选择，避免大段贴源码后只做翻译。

SVG 图中的组件、箭头、状态或数据布局应能映射到证据。正文附近说明图的阅读方式和必要限制；示意关系与真实测量区分开。架构图不必画出所有组件，机制图也不必完整重复整体架构，选择能解释本篇问题的抽象层次。

将研报与被引用的独立 SVG 一起写入 `output/`；图片引用使用相对路径。交付前打开或渲染图形检查实际效果，无法渲染时说明没有做视觉核验。基础检查不能证明布局清楚、事实正确或读者已经能理解。
