# 恢复与新提交复测

## 中断后继续

先运行 status，实际状态以 state.json 为准。代码、清单、环境都没有变化时保留已有结果，继续待测试的场景。

- 代码指纹发生变化：停止把当前工作区当作原 PR 版本，不接受未提交修改。重新解析已提交的新版本并准备干净的隔离工作区。
- 计划变化：重新确认范围与环境，旧结果失效，历史发现与证据保留。
- 数据或服务环境变化：重新记录 environment，不沿用旧环境的通过结果。
- 命令未完成：先确认它是否仍运行，检查测试数据副作用。确认结束后用 interrupt-command 记下原因，再决定是否重试；不能将未完成命令改成成功。
- 需求、环境或产品决策仍缺失：保留 blocked 和继续验证需要的条件，不为清空清单把它改成 pass。

工具用单写者锁和原子替换保存状态；并发写同一 run 会被拒绝，进程退出后锁释放。

## 开发者提交新版本后

本 Skill 不执行修复。新提交来自用户或独立的开发流程。

1. 对同一 PR 重新运行 pr_workspace.py，固定新的 base/head 并建立另一份干净工作区。
2. 用 `refresh --run "$RUN" --context next-context.json` 切换测试上下文。PR 身份须保持一致。
3. 按新差异检查清单；有新文件时补场景或排除理由。确认新的服务和测试数据。
4. 实际执行原失败场景和相关回归，保存当前提交的操作、日志、截图或视频。
5. 新提交与原失败提交不同、预期及依据保持一致、本轮场景通过时，报告自动产生“新版复测通过”记录。

如果改了预期、只有环境变化，或尚未实际复测，不把原问题标成新版通过。原失败报告、提交和证据继续保留。当前实现保守地使上下文变化前的全部结果失效，不自动猜测哪些旧 Pass 可以复用。

## 排查与建议

可以阅读必要源码帮助理解影响范围、判断问题归属。报告中的 cause_hypothesis 写可能原因并说明待确认，recommendation 写建议的处理方向；两者都不表示已修改或已解决问题。

只执行与改动相称的现有测试。临时诊断脚本放在任务目录，测试数据与日志放在获准的隔离环境；不往被测产品代码中插入修复或新增断言来制造通过。

## 收尾

报告绑定实际被测提交，包含失败、偶发、未验证与排除项。结束本轮创建的服务和会话，清理本轮测试数据；保留复核和恢复所需的工作区及证据。不要结束用户原有服务，不将认证状态打入报告包。
