# 反馈迭代与经验提炼

用于已有 SVG 的连续改图，以及用户明确要求把图稿和沟通经验沉淀为案例。普通改图不自动扩充 skill；收录结构见 [案例索引](examples/index.md)。

## 默认升级图稿版本

优化反馈默认生成新版本，不覆盖已有交付图。只有用户明确要求在原图修改或覆盖时才原位更新；指出原文件路径本身不代表要求覆盖。用户直接指定 `-V2` 等后缀时沿用该后缀。

- 没有版本后缀的图视作第一版；新交付用 `name-V2.svg` 与 `name-V2.png`。已有 `-Vn` 时按同一图稿系列递增，检查 SVG 和 PNG 两种路径，避免覆盖任一已有文件。
- 新版本从上一版继承有效内容与约束，再执行本轮修改；无需为了新版本重做整图。
- 同一轮调试可更新尚未交付的新文件并使用 `--overwrite` 重渲染；这不授权覆盖上一交付版本。
- 更新正文或案例索引指向新版，并明确交付新旧路径。旧版保留可访问，删除历史需用户明确要求；不将“现在引用新版”当成删除旧图的依据。
- 案例目录的稳定身份与图稿版本分开：同一案例目录里可有 `ecosystem.svg`、`ecosystem-V2.svg`，不用为每次优化复制一个新案例。

## 把一轮反馈变成明确变更

先识别反馈改变的是哪类对象，再修改对应部分。区分“本轮新增／撤回的要求”“仍有效的既有决策”“受本轮影响需复核的关联”，可用短清单记录，不必保存完整聊天。

| 反馈类型 | 修改对象 | 需要复核 |
| --- | --- | --- |
| 系统边界、分类、角色、主流程 | 对象和关系 | 成员、来源、箭头方向是否仍成立 |
| 静态架构和流程挤在一起 | 阅读区与阅读方向 | 拆分后同一对象的命名、职责仍一致 |
| 宽一点、矮一点、某组靠近 | 分栏、坐标和间距 | 字号、形状比例、标签和连线留白 |
| 加粗、换色、换图标 | 指定对象的视觉属性 | 对比、素材比例、主次关系 |
| 补齐目录、版本或证据 | 产物及其引用 | 共同根路径、来源与结果不会混淆 |
| 暂定、可选、还没实现 | 对象标签与图稿状态 | 标题／说明／PNG 中不残留已实现的暗示 |

结构性反馈先解决结构，再做文字和装饰调整。只影响一个节点时局部修改；反复纠正同一类问题时，重新检查抽象层次或阅读路径，而不是继续微调颜色。

保留未被撤回的名称、成员、素材、职责和已确认布局。改名或移位时同步它的连线、遮罩和说明；不要每轮从头生成导致先前要求丢失。导出新 PNG 后实际查看，尤其是本轮改动和受影响邻近区域。

## 从案例提炼方法

按“可观察的问题 → 实际调整 → 为什么有效 → 适用条件”提炼。把反馈转为可验证的条件，例如“请求箭头从调用方落到服务方，返回箭头方向相反”“完整目录分栏后仍共享同一根路径”，不要仅写“更清晰”“更高级”。

将三类内容分开放置：

- **通用方法**：会改变其他任务的判断或执行方式，进入对应方法参考，并从入口路由；已存在的方法直接引用。
- **案例取舍**：本图的配色、比例、角色数量、金字塔或消息气泡等，进入案例说明，写清为什么适合本图。
- **可复用图稿**：最终源图、认可预览及有教学价值的少量变体，进入案例资产目录；不积累每轮草稿和临时生成脚本。

“采用三泳道”通常是实例；“跨系统协作按实际责任放动作，再用方向和标签区分请求与返回”才是方法。不要把本例的固定数量、特定品牌或方案中的文件名升格为所有任务的要求。

## 区分反馈证据与设计推断

有原始对话时，摘要记录改变决策的请求及响应，不复刻逐句聊天、个人信息或无关内容。有 Git 历史时，可用提交和图稿差异说明“发生了什么变化”；只有提交文字明确写了请求时，才将其视作间接反馈证据，并注明来源。

仅有最终 SVG／PNG 时，可以分析“画面如何组织”和“可能适合什么任务”，不能编造修改轮次或用户原话。缺少完整对话不妨碍收录图稿，但案例要说明这一限制。推断出的理由标为分析，不冒充用户确认或当时的设计动机。

后续增加的优秀图稿应补充新的表达能力或明确的新经验，而不是重复复制相同规则；同图优化在原案例内维护下一版本及其说明；只有明确要求原位修改时才更新同名图稿。
