# 功能设计图构图

用于解释“一项功能如何工作”，如知识索引、产物发布、同步、评审和交接。生态图强调有哪些能力、归属谁；功能图强调输入如何形成输出、用户怎么读取、更新或失败时发生什么。相关案例：[Raven Wiki 功能设计图](examples/raven-wiki-feature.md)。

## 先整理四类内容

| 内容 | 先回答的问题 | 画面中的常见形式 |
| --- | --- | --- |
| 输入与加工 | 事实来自哪里，谁按什么规则处理 | 资料集合 → 处理者／规则 → 产物 |
| 产物与引用 | 真正保存什么，哪个对象把内容串起来 | 清单、索引、引用和必要版本标识 |
| 使用视图 | 哪些人或 Agent 如何取得和读取内容 | 并排的阅读面板、导航或目录示意 |
| 更新与冲突 | 何时重算、校验什么、成功或失败怎么办 | 独立窄栏、分支与回路 |

按任务选用，不要求每图都具备四类。先用一句话概括主线；内部实现细节仅在影响读者判断时进入主图。密集子过程可另出细节图。

## 安排主次与阅读路径

- 主过程优先占据阅读区，从左到右或从上到下贯通。更新、发布、异常可放在侧栏，用分隔和次级标题帮助读者找到它，不让多条流程竞争同一阅读起点。
- 同一产物供不同角色使用时，从共同产物向多视图分支；不要只因画了两个面板就画成两套数据源。
- 面板以“角色如何完成任务”决定内部形态：给人的导航与页面片段、给 Agent 的索引文件与相对路径可以不同，但对应对象、内容和版本应一致。
- 展示 UI 或文件目录只需保留能说明机制的部分，避免画成完整软件界面。目录分支用层级线，执行步骤用箭头，二者不混用。

主区宽、侧栏窄是 Wiki 案例的选择，不是固定比例。版面由说明长度、并列关系和实际展示尺寸决定。

## 把关系画准确

- 找到“共同依据”并让它在画面中可见，例如清单、配置、工作包或来源记录。重复出现相同标识是为了帮助读者核对同一对象，而不是装饰性徽标。
- 区分不同版本维度：发布版本、来源提交、资源版本、编辑基线不是同一个值。不为省空间把它们合成一个“版本”。示例编号应标明为示例，并在各视图与分支保持一致。
- 输入原文、派生说明、引用路径与渲染结果分开命名。只下载说明与索引，就不画成下载全部原文；按本地路径读取，也不画成远程同步副本。
- 校验节点写出改变结果的条件；发布成功后指向真正更新的入口或产物。冲突后画出保留、重新读取和再提交的路径，不能让失败箭头也落到成功产物。
- 实线／虚线若用于区别主线、回路或跨区联系，应有一致含义并能从标签读懂。不为填空白增加无含义的双向箭头。

## 层次与可读性

强调关键产物、主视图或分支结果即可，辅助资料与步骤保持中性。区分可用色块、标题条、边框或位置，不依赖每个框一种颜色。配色与字体优先沿用当前项目，而不是照搬案例里的浅蓝、浅紫。

每框保留“对象名称 + 必要动作／判断”两层信息；代码路径用适合字面标识的样式。若正文已经解释细节，图中不重复长段落。局部强调不应让主流程中的其他文字在正常展示尺寸下不可读。

## 核验这类图

从输入走到最终可用结果，检查每条箭头都能用一句话解释。再分别走一次更新成功与冲突路径，检查来源、编辑基线与发布版本是否前后一致。最后以每个使用角色的视角，检查它实际取得什么、在哪里读取原文、哪些对象是共享引用。

示意方案不等于上线事实；一张图没有画出的权限、超时等分支也不表示系统没有这些情况。案例未包含的语义不要在复用时自行补成实现承诺。
