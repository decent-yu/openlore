# 可读性自查与改写示例

读者有基本技术常识，但可能第一次接触本篇主题。交付前按这个视角通读：能否说清在解决什么问题、方案怎样工作、为什么有效、有什么限制？发现问题时直接改正文，不把自查过程写入文章。

## 常见问题

| 问题 | 改法 |
| --- | --- |
| 开头就讲架构、协议或算法，没说用途 | 先给具体场景，再说明方案和适用条件 |
| 一个句子堆叠“解耦、编排、治理、一致性”等名词 | 写清谁做了什么、结果是什么，补足中间因果 |
| 只翻译术语，或只给缩写的英文全称 | 就地解释它的用途，再按需要保留准确名称 |
| 用新术语解释另一个术语 | 回到具体动作或例子，不让读者为了读懂一句话继续查词 |
| 只有类比，没解释真实技术 | 类比之后说明实际步骤、成立条件和类比的边界 |
| 段落很短，却全是结论和清单 | 用连贯句子解释原因和过程，一段讲清一件事 |
| 为了凑篇幅，每篇都写架构对决、排障树、落地路线 | 只保留当前主题需要且有证据支持的内容 |
| 用“赋能、闭环、重塑范式”代替事实 | 写具体动作与结果；没有测量就不填效果数字 |
| 为追求简单省略了条件 | 保留版本、前提、成本、局限和不确定性 |
| 标题抽象，或附带装饰性英文后缀 | 直接写读者的问题或要做的动作 |
| 图里全是缩写、箭头没有含义 | 使用中文动作标签，交代阅读顺序，必要术语先在正文解释 |

## 示例一：解释机制而非堆叠术语

难读：

> 通过幂等语义与持久化检查点，实现工具调用的可恢复执行。

改写（以下是解释机制的假设例子）：

> 假设 AI 调用转账工具后超时了，钱可能已经转出。此时直接重试，可能重复转账。可以给这次转账一个固定编号，重试时沿用这个编号，让收款系统识别重复请求；这种重复请求不会再次转账的保证叫“幂等”。同时保存任务已经做到哪一步，也就是“检查点”，方便重启后继续处理。
>
> 两者要配合使用：保存了本地进度，也不代表知道收款系统是否已经完成转账。还需要查询转账结果，或由收款系统按固定编号去重；只有本地记录无法保证不重复转账。

这里补出了场景、动作和限制，后文仍可继续分析请求编号和状态保存的实现。

## 示例二：具体表达不等于补数字

难读：

> 该方案深度赋能研发团队，使交付效率提升 80%。

资料只说明功能、没有测量时，可以写：

> 这个工具能自动修改代码并运行测试，减少手动操作。资料没有提供完整交付周期的测量结果，暂时无法判断能节省多少时间。

有真实测量时再引用数字，并写清测量对象、环境、基线和来源。不能把写作示例中的数字当成真实结果。

## 示例三：公平比较两种做法

难读：

> 传统轮询已经落后，事件驱动架构能够解决所有高并发问题。

可以这样解释差异，具体结论还需结合所研究系统的证据：

> 定时轮询就是隔一段时间查一次有没有新任务，实现比较简单，但任务可能要等到下次查询才被发现。事件驱动是在新任务到来时发通知，减少等待；代价是还要处理通知失败或重复送达。应结合任务量、允许的等待时间和维护成本做选择，不能只凭方案名称判断优劣。

## 最后检查

- 首段是否说明问题、做法和适用场景，读者是否需要查词才能继续？
- 关键术语是否在首次出现时解释？例子是否足以帮助理解，而非引入更多新概念？
- 从输入到结果的关键步骤是否连贯？是否用抽象名词跳过了原因？
- 原文事实、外部证据、假设例子与分析建议是否分清？引用与量化结论是否有出处？
- 是否写清代价、局限和未知项，避免把单一案例推广成普遍保证？
- 章节、表格和图是否有实际解释作用？是否存在重复或为凑数添加的内容？
- 正文是否没有独立的 `---` 分割线？图中文字是否可读，引用的文件是否存在？
