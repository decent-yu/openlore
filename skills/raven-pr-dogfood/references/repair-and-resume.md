# 修复、恢复与收尾

## 先判断是否可以修复

用户要求 QA 并修复时使用 repair；否则只交发现。明确的小错误可以在授权范围内直接处理，涉及产品意图、架构、数据模型、兼容策略或多个合理方案的，记录问题、选项和建议，不为清空清单自行决定。

适用的产品规则若与 PR 明确的意图冲突，先查明它是否已过期。报告规则来源、PR 的选择和影响；不能为满足旧规则反向破坏本次需求。没有专用规则包解析依赖，直接读取项目已有的需求、验收和人物资料，并注明来源。

## 行为修复的实际顺序

1. 保存初始失败/偶发观察、复现前提与证据，形成当前场景发现。
2. 定位根因，准备最小且能捕获该错误的回归测试。新测试属于代码变化，先 refresh、更新 plan 的路径覆盖并重新确认环境。
3. 以 phase=before 实际执行回归，检查失败是业务断言触发，不是导入失败、缺依赖、网络不可达或根本不存在测试。
4. 修改源代码，不改变该回归的命令与预期来“修绿”。范围应限于根因与必要调整。
5. refresh 使旧结果失效；把新文件纳入计划，重新确认环境，在 phase=after 下执行同一回归命令，再实际复查原用户场景及相邻场景。
6. 当前场景记录为 pass 后，提交 repair JSON。工具比较前后命令、代码指纹、退出码、次序以及证据，防止只写一段“已修复”。
7. 运行当前项目相称的自动化 suite，交付修复文件、根因、前后日志和场景复查。套件失败要如实记录，不能靠目标场景绿灯掩盖其他回归。

首次代码变化前保留的发现不会消失。若添加测试时替换计划，历史发现仍在 history；更新版本后旧证据只能证明旧版本。回归命令须是一次性测试进程，不是开发服务器或持续 watch。

纯视觉修复允许 visual_reason 例外：说明为什么没有有意义的自动化断言，并用实际截图/浏览器重走证明。工具不能自行判断理由充分与否，最终报告把它单列。

## 提交与新版本

本 Skill 不硬编码自动提交。用户或项目工作流要求 commit 时，遵循已有授权；commit 改变 HEAD，工具会使旧结论失效。需 refresh、重建环境依据、重新执行相关场景及套件，再交付与最终代码一致的结果。报告产物保持在工作区外，避免为了记录报告又产生递归的版本失效。

只有本地修复未提交也可交付，报告同时记录 HEAD 和工作区指纹，并告知修复所在隔离工作区。推送、发布报告、PR 评论或合并均不是运行本 Skill 自带的动作。

## 中断恢复

先运行 status，并查看旧报告与 history。状态以 state.json 为准，不以终端记忆为准。

- 代码、计划、环境都没变：保留已有结果，继续 pending 和有明确验证条件可解决的 blocked。
- 代码指纹不同：report 模式不能接受任意本地编辑；重新解析更新后的 PR context。repair 模式可 refresh 接受本轮授权修复。
- 环境/数据变更：重新记录 environment；旧环境结果不再计为通过。
- 当前实现保守地使一轮中的全部结果失效，而不猜测只失效哪一项。旧日志和证据不会删除，重测后能清楚看到前后区别。
- 命令未完成：先检查它是否仍运行。不要重放可能有副作用的命令；确认退出并检查测试数据后用 interrupt-command 记录中断原因，再决定重试。
- 复查时未解决的需求/环境/产品决策继续保持 blocked；不重复询问同一个已经记录的决策，也不把 blocked 改成 skipped 或 pass 清空清单。

工具通过单写者锁和原子替换保存状态；并发修改同一个 run 会被拒绝，进程退出后锁释放。多个独立 run 可以并存，但不要让它们同时写同一份测试数据。

## 交付检查

交付包里应该能顺着“改动 → 旅程 → 场景 → 实际尝试 → 文件证据 → 修复/回归”查清结果。工具检查文件、哈希和状态关联，模型仍要复读报告，核对实际预期、归属、例外与范围是否合理。

结束本轮创建的服务和浏览器会话；停止前先记录身份/归属，不能关闭用户已有会话。保留必要的未提交修复、证据和恢复状态，告诉用户路径。认证状态不属于证据，单独存放并按用户的会话保留偏好处理。
