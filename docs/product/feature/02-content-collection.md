# 采集与候选选择

## 目标与三层数量

明确区分：**发现了多少条目 → 读取了多少篇正文 → 最终入选多少篇**。发现条目不等于全部调用 AI，也不等于全部写入仓库；文件数量由入选文章和产物规则决定。

公共来源轮询与采集组运行分开。来源负责发现并缓存元信息；组到期或用户点击“立即运行”后，才按该组范围挑选候选、补抓正文并进行处理。

## 来源轮询

1. 每 30 分钟检查被启用组引用的来源；同一来源、配置与凭据范围只抓一次。间隔按来源可配置。
2. RSS/Atom 请求复用 ETag/Last-Modified；304 表示没有新的 Feed 响应，但仍继续处理本地积压、已失败补抓与未完成交付。
3. 解析响应中所有可见条目，保存上游 ID、URL、标题、作者、发布日期、更新时间、摘要及已有正文；不假设 Feed 已按日期排序。
4. 来源内用上游 ID 识别条目，无 ID 用规范 URL；跨来源按确认的规范 URL 关联同一文章，保留所有出处。只清理明确的跟踪参数，不删除有业务含义的 query。
5. 新 ID、新的上游修订或实际内容 hash 变化建立新版本。原站未通过 Feed 声明正文更新时，首期依靠用户“重新抓取”检测，不承诺即时发现此类更新。
6. 每次最多 10 个请求、100 个条目的处理分片，剩余响应快照先落盘后续读；不得因为保存新 ETag 丢掉未处理的尾部。完整 Feed 仍不代表网站全部历史。

元信息和失败原因保留 90 天；已入选文章的正文、版本与证据持续保留。原始 HTML 默认保留 30 天，受未完成任务引用的材料延长至任务结束。

## 一次采集组运行的确定规则

运行开始固定组配置和连接修订，创建 run_id。首次没有缓存或来源缓存已过轮询间隔时，先刷新相关来源；随后固定候选截止时间 T。某源刷新失败时仍可处理已有缓存及其他成功来源，并标注覆盖缺口。同一运行重试保持身份和已确定的截止时间不变。

| 顺序 | 判断 | 行为 |
| --- | --- | --- |
| 1 | 来源停用、组暂停、连接未就绪 | 不启动对应动作；显示 disabled/blocked，不能伪装成零更新 |
| 2 | 首次关联来源 | 保存起始覆盖时间 `coverage_start=T-7天`，纳入此时间后、T 之前发布或明确更新的可见条目；指定单篇 URL 不受此窗口限制 |
| 3 | 后续增量 | 沿用该来源在本组的 coverage_start，纳入范围内新发现或已变更且未按当前规则处理的条目；已登记积压不因等待而失效，重现的范围外历史条目不自动混入 |
| 4 | 无发布日期 | 以首次发现时间进入候选，标注 date_unknown；不伪造发布日期 |
| 5 | 本组已经成功处理相同文章版本与规则 | 复用结果；已交付者跳过，待交付者走原文件包重试 |
| 6 | 多来源候选较多 | 每个来源按 first_seen_at、稳定 ID 排序，来源间轮转取数；规范 URL 重复只占一个名额 |
| 7 | 候选数超过 20 | 本批只评估 20 篇，其余保持 pending，下批继续；不是 rejected |
| 8 | 候选已有可用全文 | 复用本地正文；只有摘要、未知完整度或明确更新时调用 web_page 补抓 |
| 9 | 正文失败或仍不完整 | 记录待补全与重试，不消耗最终入选名额，不生成伪全文摘要 |
| 10 | 进入内容处理 | 执行 03 的明确关键词/AI 规则，最多选 10 篇；达到质量门槛但超过名额者保留待下批，复用评分 |

时间窗属于组的选择规则，不应让共享采集器提前丢弃其他组可能需要的条目。管理员的来源预算限制网络资源，组的候选与入选上限限制处理量。首次回看窗口与 20/10 上限均可配置。

单篇 URL 导入必须选择目标组，记为系统“手动导入”来源，不自动新增网站订阅。它不受首次日期窗口限制，使用组关注描述与内容偏好做 AI 评估，不套用另一个网站的关键词。跟随重定向后与已有文章合并；“重新抓取”只刷新该文章并建立有变化的新版本，不额外制造重复文章。

## 数量示例（示意数据）

两个来源发现 36 条，合并 4 条重复后剩 32；排除 6 条首次窗口外内容、跳过 5 条本组已处理内容，得到 21 个候选。

本批取 20：2 篇正文失败待重试，3 篇不满足关键词，4 篇未达到 AI 门槛，11 篇合格。最终入选 10 篇；另外 1 篇合格内容和最初剩下的 1 篇均延后。结果是 **10 入选、7 排除、2 待补全、2 延后**，每一条都有去向。

## 统一接入约定

`collect(request, context) -> CollectionResult`，支持 `discover` 和 `fetch` 两种操作。

| 输入 | 输出 |
| --- | --- |
| 来源/配置修订、能力 ID、操作、目标 | 稳定条目标识、原文/最终 URL、元信息、正文及格式 |
| 时间或页范围、批量上限、续采状态 | 正文完整度、附件缺口、原始依据引用 |
| 凭据引用、能力参数、请求和时间预算 | success/partial/failed/not_modified、覆盖范围、下一状态、结构化错误 |

完整字段见[采集接入设计](../../design/collection-adapters.md)。每项能力独立目录；第三方 SDK 返回结构由适配器转换，业务流程不依赖网站名或厂商返回格式。下游不得将 HTTP 成功或非空文本直接认定为全文成功。

## 接入清单

| 能力目录 | 本期 | 实现方式 |
| --- | --- | --- |
| `collectors/web_feed/` | 是 | [feedparser](https://feedparser.readthedocs.io/en/latest/) 解析 RSS/Atom；共享 HTTP 层负责预算和条件请求 |
| `collectors/web_page/` | 是 | HTTP + [Trafilatura](https://trafilatura.readthedocs.io/en/latest/)；支持文章导入、补抓和调研引用页获取 |
| `media_assets/` | 是 | 提取正文图片、下载原始字节、内联 SVG 归档与本地路径映射；受 03 的完整性和预算规则控制 |
| `collectors/github_api/` | 后续 | 官方 API，获取 Releases 等；区别于仓库文件同步 |
| `collectors/web_browser/` | 后续 | Playwright，处理动态页面 |
| `collectors/web_service/` | 后续 | Firecrawl 等托管能力 |
| `collectors/x_platform/` | 后续 | 平台接口或工具，认证与覆盖范围单独验收 |
| `collectors/wechat_platform/` | 后续 | 公众号服务；已输出标准 Feed 的服务直接复用 web_feed |

本期 Cloudflare 和 Simon 共用 web_feed，不为两个网站创建两套代码。独立注册、配置校验和统一契约是新增能力的接入条件。

## 错误、续采与可见性

- 网络错误按 30 秒、2 分钟、10 分钟最多重试三次；限流优先遵循 Retry-After；凭据失效直接 blocked，修复连接后可恢复。
- 条目、原始快照和待补抓任务持久化后才推进来源状态；解析不完整不能静默推进完整检查点。
- 单源失败仍让其他来源继续。运行页面分别显示 observed、duplicate、out_of_scope、already_processed、candidate、body_failed、selected、excluded、deferred。
- 人工重试恢复失败阶段；不会重新采集成功来源或重新生成已固定的文件包。

## 验收

覆盖 RSS、Atom、304、无日期、无 ID、乱序、重复、重定向、摘要补抓、预算截断和断点恢复；用真实来源验证一次，再用固定输入验证上面的数量守恒。停止服务后重启，积压与失败记录仍在，已成功条目不重复发布。

文章配图在入选后由独立图片能力归档，采集条目保存配图清单与原始 URL。图片失败使用 pending_assets，重试不要求重新生成文章或重复拉取已成功图片；具体策略见 [03](03-content-processing.md)。
