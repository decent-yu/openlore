# 来源配置

分为两个交互模块：管理员维护可用信息源，用户从中选择来源，建立自己的采集组并配置筛选与同步目标。

## 首期信息源

| 信息源 | 主要内容 | 选用理由与筛选重点 |
| --- | --- | --- |
| [Cloudflare Blog](https://blog.cloudflare.com/) | 网络与安全、数据库、性能优化、云基础设施，以及 Agent 工程实践 | 获取一手工程分析；优先技术原理、实现细节与故障复盘，降低纯产品公告的优先级 |
| [Simon Willison](https://simonwillison.net/) | LLM 工具、编程 Agent、开发方法、实际实验与技术评论 | 补充 Agent 实践视角；优先原创分析和可复用经验，区分长文、短评与外链推荐 |

两者均通过订阅源发现内容，必要时补抓原文。网站采集入口、验证记录和后续候选统一维护在[网站信息源清单](../research/03-minimal-prototype/02-web-source-catalog.md)。

## 模块一：信息源管理（管理员）

管理员决定系统提供哪些来源，并维护来源说明和实际采集入口。

| 配置 | 内容 |
| --- | --- |
| 来源说明 | 名称、网站地址、主要内容、适合关注的主题、内容特点与局限 |
| 采集设置 | 启用状态、采集类型、订阅地址或文章 URL、处理范围及必要的访问凭证 |

首期支持 RSS/Atom 和单篇 URL。来源说明中的主题是帮助用户选择的内容标签；实际筛选条件由用户在采集组中设置。

交互：管理员查看来源列表 → 新增或编辑来源 → 配置入口和范围 → 启用或停用。用户可查看来源说明，从已启用来源中选择，不修改公共来源的采集设置。

## 模块二：采集组配置（用户）

用户可以创建多个采集组。每个组独立表达“关注什么、从哪里获取、同步到哪里”。

| 配置 | 内容 |
| --- | --- |
| 分组名称 | 如“Agent 相关知识”“后端性能优化” |
| 关注描述与筛选偏好 | 说明组内关注方向；如优先实现细节、代码、实验数据或明确技术取舍 |
| 组内来源 | 从管理员提供的来源中选择，可添加多个来源 |
| 来源关键词 | 为组内每个来源分别配置关键词，细化该来源在本组中的关注范围 |
| Git 同步 | GitHub 仓库地址、仓库内归档路径、目标分支、绑定的 GitHub Token 凭据；分支不填时使用仓库默认分支 |
| 消息同步 | 消息推送 Webhook 地址 |

交互：创建采集组 → 填写名称与关注描述 → 查看来源说明并添加来源 → 分别设置关键词 → 填写同步目标 → 保存。用户可继续创建、编辑其他组，或调整组内来源。

关键词用于表达筛选意图，具体匹配方式在内容处理功能中明确。

## 示例

```text
采集组 1：Agent 相关知识
  Git：<仓库地址>，路径 knowledge/agents/
  消息：<Webhook A>
  Simon Willison：agent、tool calling、context engineering
  Cloudflare Blog：agents、MCP、Workers

采集组 2：后端性能优化
  Git：<仓库地址>，路径 knowledge/performance/
  消息：<Webhook B>
  Cloudflare Blog：database、latency、performance
```

示例展示配置关系，不预设实际仓库或 Webhook。

GitHub Token 与 Webhook 等凭据单独保存，组配置通过引用绑定；同步规则见[推送与 Git 沉淀](04-delivery-and-git-archive.md)。

## 关键规则与预期结果

- 同一来源可以加入多个采集组；各组的关键词、关注描述和同步目标独立。
- 公共来源启用后可供用户选择；停用后不再参与采集，受影响的组应显示来源不可用。
- 内容按采集组分别筛选与汇总，并同步到该组配置的仓库路径和 Webhook。同一条内容可以符合多个组。
- 修改一个组的配置不改变其他组；公共来源的采集设置由管理员统一维护。
- 管理员能维护来源，用户能创建至少两个采集组，使用不同关键词与同步目标，验证结果按组区分。
