# 01 来源采集

入口 `/sources`。来源独立发现候选、补抓原文并执行质量准入；只有通过准入时才创建内容池文章。

## GitHub 仓库研读

来源支持 RSS / Atom 与 GitHub 仓库。选择“GitHub 仓库”，填写仓库根地址（如 `https://github.com/stablyai/orca`）和用户自己的研读目标；历史研读内容由每次任务自动关联，包括已归档研报、未完成状态及失败原因。配置不调用 AI 生成计划，不维护额外主题列表。修改目标保留所有历史报告。

一个“仓库研读”流水线可关联多个仓库，统一设置每天运行时间、每次执行时每个仓库的调研篇数 M、AI 执行器及归档目录（如 `docs/xxx`）。来源范围留空表示全部同类型来源。选择仓库时预览各自目标和历史，并可跳转来源编辑；多条流水线共享来源数据，不提供任务级目标覆盖。

控制服务只管理仓库地址、目标与历史，分配研读记录并调度任务，不拉取源码、读取 README 或维护源码缓存。GitHub 来源不执行定时采集，也不提供“立即同步”；运行关联流水线后，由 AI 执行器准备源码。

每次新研读由执行器更新默认分支，在本机缓存并检出源码，准备 README 等上下文。控制服务保存执行器返回的版本信息，但 Commit 只作参考，不要求 AI 填写或校验，也不要求同批报告版本一致。生成后不再复查源码版本或工作区变化；通过 Skill 提示只读源码。子模块和 LFS 不自动下载。

仓库按最近分配时间轮换，每轮每仓库一个名额，再轮到下一仓库；M 是每次流水线执行时每个仓库各自的篇数上限，同一天再次执行也按 M 分配，不扣减当天已归档篇数；多个仓库互不占用名额，失败或待归档研读的重试占用本次名额。来源目标、历史标题、研究问题及报告全文共同提供研究上下文，完整上下文写入 AI 工作区 `input/research-context.json`，实际 Prompt 与流水线预览共用构建逻辑。首篇系统介绍项目用途、整体架构和代表性执行链路，后续根据当前源码自主选择值得深入的问题，历史只作线索，可以补充或推翻既有结论。AI 在实际研读时追踪尚未深入的机制，追踪调用方、实现、数据结构、异常处理、测试和设计文档。仓库不执行文章来源的准入、选文、初审或翻译。

独立 `github-code-research` Skill 交付中文研报 `output/research.md` 和必要配图。不要求 `evidence.json`、精确行号、逐字引用、引用数量或 Commit 校验。重要结论尽量说明对应文件、函数或普通源码链接；无法确认的内容如实注明。质量重点是项目用途、架构、调用链与设计取舍。源码无法拉取或读取时失败；CLI 失败但已保存有效研报时仍接纳该产物，不为引用问题切换备用模型或重新生成。

卡片中的“重新发起深度调研”同样先更新真实默认分支源码，再围绕原问题复核；新研报直接替换原归档路径，保留原编号，旧内容可从 Git 历史追溯；研究记录独立保存各次实际 Commit 和材料版本。重试归档只复用已批准的研报、原快照和路径，不会重复生成。

调研记录在生成前持久分配稳定 ID；失败保留原因，下次重试同一记录并更新代码。生成成功但归档失败时，保留原报告、证据、代码版本与已分配路径；即使目标、Prompt、Skill 或默认分支已经变化，也只重试交付。新研报记录包含代码调研 Prompt、Skill 版本、来源目标与历史要求、执行器回传的实际代码快照及执行器信息。已完成记录跨流水线共享，避免重复研究。

只有本地 / Worker / SSH 执行机需要研读源码所需的 Git、仓库网络与读取权限。执行机使用自身 Git 凭据；同机 `local` 模式也可读取本机保存的默认 GitHub Token。控制服务的 Token 用于归档，不随任务下发。HTTPS Token 通过临时进程环境使用，不写入 Git URL、命令参数或仓库配置。源码准备时间计入执行器超时。不要求执行器必须回传 Commit；源码不可读取时不回退到文章研读。升级时同步更新控制服务和 Runner。专用 Skill 的同步模式自动传送文件；本地 Skills 模式需在执行机配置目录安装并刷新 `skills/github-code-research`。

研报第一行标题用于连续编号命名。研报与必要配图归档成功后，才进入共用首页、每日研报、汇报预览和 Webhook 链路。目录结构见 [GitHub 交付归档](05-git-delivery-and-archive.md)。

## RSS / Atom 规则

- 默认每 30 分钟发现新条目；待补抓和未完成的 Feed 分页每轮调度继续处理。
- 默认采集今年内、最近 30 天首发的文章，首次同步同样遵守。超期内容直接拒收，不进入内容池。
- 默认从原文明确的发布日期元数据核验日期，区分首发、修改与发现时间；缺失、未来或冲突日期不直接进入可读池。
- 主题关键词支持词边界、常见概念变体。辅助模式允许 harness、模型路由、评测等明确工程主题补充命中，其他未命中内容留待复核；严格模式必须匹配关键词。
- 排除关键词和来源分类独立配置。默认排除 Company、Company Announcements、Global Affairs。
- 摘要与空内容补抓正文；失败记录原因，临时故障最多重试三次，HTTP 401/403/404 等直接标记失败，重评可重新尝试。

## 状态和同步

待补全文和待复核候选仅存在于后台采集队列，不创建文章、正文版本或内容池来源关联。通过准入后才进入 `articles` 和内容池。可用内容表示日期、正文和主题初筛通过。新文章成功入池后自动排队进行共享内容初审，采集不等待 AI 完成；初审失败仍保留池内正文与失败原因。

超期、规则拒收和最终失败候选丢弃正文与独立原始页面，只保留 30 天的诊断详情；到期仅保留身份、内容指纹和规则版本用于去重，避免反复抓取。规则改变允许重新发现。

来源卡展示准入、待处理、超期拒收、规则拒收和失败统计。保存规则只重评未入池候选，也可手动重评。文章入池后不再执行采集准入，不会因时间推移或配置变化被二次过滤。历史测试数据另行清理，不为其增加运行时豁免、迁移或保留分支。

每轮 Feed 最多发现 100 条，预览最多 10 条；剩余条目保存续读位置。发现候选先持久化，再保存 ETag；即使上游返回 304，也继续处理已排队候选。每来源每轮最多补抓 10 篇，有时间预算。补抓全文不能被后续 RSS 摘要降级覆盖。

`collection_candidates` 独立保存逐条状态、原因、重试及规则版本；`collection_runs` 保存采集配置快照与实现版本。`GET /sources/:id/quality-runs` 可查看最近运行，`POST /sources/:id/revalidate` 重评未入池候选。

Node 负责调度、规则和持久化，Python 负责 Feed 解析及正文提取。来源分类保留；URL 去掉 fragment 和追踪参数，保留语义查询参数。

内容池的“重新发起深度调研”是明确的重新生成操作：即使已有待归档正文，也更新源码并重新生成完整研报，只保留归档路径和编号。自动归档重试才复用已有正文与源码快照。

## 已有产物与历史上下文

研报生成后立即保存，即使交付未完成也进入后续研读上下文。同仓库前一篇真正失败时，已排队的后续任务停止，避免从头重复首篇；不同仓库中已成功的研报仍独立归档，批次记录为部分完成。

失败任务重试优先接纳执行器已经保存的研报和配图，不新开模型会话；日志单列“复用已有产物”，保留原始错误和尝试记录，不伪造会话续用或新增模型消耗。历史本地产物可通过 `POST /research/:id/recover` 恢复并交付；远程执行机产物需由其返回，不直接读取远端路径。
