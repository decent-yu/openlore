# 02 流水线任务

入口 `/pipelines`。任务按主题配置来源范围、审核规则、调研要求、定时计划、AI 执行器与 GitHub 归档路径。

## 任务配置

- 首行配置任务名称、执行计划（Cron）和 AI 执行器；时间默认按 `Asia/Shanghai` 执行，无需填写时区。
- 第二行填写多行的关注领域与定位，作为审核相关性的依据。
- 内容审核与评分模块配置来源范围和审核 Skill；每次最多调研篇数 M 在深度调研模块配置。
- 展开各阶段的“本阶段实际 Prompt · 查看与编辑”，可编辑审核或调研要求，并实时预览完整指令；留空使用默认要求，点击“保存任务”后生效。Skill 加载、输出格式与交付约束由系统固定。

## 选文规则

**全量内容池 → 有效审核评分 → 合格文章排序 → 每次最多 M 篇调研 → 成功归档。**

- 来源范围为空时使用整个内容池；不限定当天、最近几天或本次新增文章。
- 取消“精选入围”持久状态与精选篇数 N。只有每次最多调研篇数 M；M 为 0 时只评分。
- 相关度至少 75、工程质量至少 70，且提供可核验的原文证据才有调研资格。
- 合格候选按 `相关度 × 70% + 工程质量 × 30%` 排序，同分优先发布时间较新者；不足 M 篇时少做。
- 未取到的文章保留评分，下次继续竞争。已评分的排除文章仍保留分数与理由，满足规则变化时可重新评估。
- 评分按流水线分别计算。文章材料、任务要求、Skill 版本和执行器配置不变时复用审核缓存；展示的历史评分不代替当前配置的有效性校验。

## 调研、去重与重试

一次运行阶段为 `processing → research → delivery → completed`。来源采集独立运行，流水线只读取已入池文章。

选择调研文章时原子领取文章级占用，覆盖生成和归档全过程。不同流水线不能同时自动调研同一篇文章；已成功归档的文章默认跨流水线跳过。人工重新调研可以生成新版本，但同样不能与在途任务冲突。

研报生成成功不等于完成。`research_tasks.archived_at` 仅在 GitHub 确认交付成功后写入，首页和汇报只展示已归档研报。失败后释放占用，文章仍可进入后续运行；若相同材料和执行配置已有完整、未归档的研报，则复用它重试归档，不重复调用调研 AI。

服务重启会中断运行并清理在途占用；已保存的评分和完整待归档研报保留，手动重跑可继续复用。当前不承诺整个业务协程跨重启自动续跑。

## 运行记录

记录扫描数、已归档/在途跳过数、参与审核数、本次调研名额、低于门槛数、留待后续数，以及审核与调研的 AI 调用。`runs.output_json` 保存本次调研结果，归档成功后才标记可发布。

数据库 `group_items` 维护评分和合格/排除决定，不再作为“精选已处理”的依据。完成状态以已归档研报为准。实际执行与协议见 [AI Runner](../../architecture/local-ai-executors.md)。
