# 推送与 Git 沉淀

以采集组为单位，将[处理后的文件包](03-content-processing.md)同步到用户配置的 GitHub 仓库，持续创建或更新知识文件，并通过组内 Webhook 推送简报。

## 目标与凭据

- 每组配置 GitHub 仓库地址、仓库内归档路径、目标分支和 GitHub 凭据；未指定分支时读取仓库默认分支。
- 用户配置 Token 后，系统按授权更新目标仓库与路径中的管理文件。Token 单独保存，通过凭据引用使用，不写入生成文件、仓库 URL 或日志。
- 首期使用 GitHub Token，权限需覆盖目标仓库的内容读写；目标分支须可写，受保护分支按仓库规则处理。
- 每组配置自己的消息 Webhook。GitHub 同步和消息推送使用独立能力目录与结果记录。

## 统一输入与输出

| 输入 | 约定 |
| --- | --- |
| 文件包 | 组标识、批次、文件相对路径、文件内容及摘要值、管理清单 |
| GitHub 目标 | 仓库、分支、归档路径、Token 凭据引用 |
| 通知目标 | Webhook 引用、组内简报与对应的归档链接 |

| 输出 | 约定 |
| --- | --- |
| 仓库结果 | 已更新、无变化、失败、冲突或结果待确认；提交 SHA/链接、变化文件和错误 |
| 推送结果 | 已发送、跳过、失败或结果待确认，以及可用的消息标识 |
| 批次状态 | 各组、各目标分别记录，便于恢复与核对 |

具体接口与 GitHub 写入流程见[处理与同步设计](../../design/processing-and-delivery.md)。

## 同步流程与文件规则

读取目标分支最新状态 → 对比文件包与已管理文件 → 创建或更新变化文件 → 提交到目标分支 → 确认仓库结果 → 推送带归档链接的组内简报。

- 新文章创建文件，已有文章更新同一路径；索引和管理清单同步更新。内容无变化不制造空提交。
- 一组一批文件作为一次提交交付，避免文章已更新而索引未更新。
- 只修改本组归档路径内明确管理的文件；已有同名文件无法确认归属或人工修改产生冲突时，报告冲突。
- 首期执行新增和更新；本次未入选的历史文章不因此删除。不同组的管理路径不能相互重叠覆盖。
- 保留仓库其他文件和提交历史；遇到并发提交重新读取并比较，不强制覆盖远端。
- GitHub 成功后再推送消息。消息失败仅重试消息，仓库失败保留文件包；请求超时先核对实际结果，避免盲目重复交付。

## 能力接入与验收

- 本期接入 `github_repository`：优先使用 GitHub 官方 API/成熟客户端完成文件更新。
- 本期接入 `webhook_notification`：对接一个确定的消息平台，按平台业务响应判断成功；具体平台在实施前确定。
- 适配器只处理目标系统交互，不重新筛选内容或调用模型生成文章。
- 验证真实 Token 可写入指定仓库与分支；新增、更新、无变化重跑均符合预期。
- 验证组间路径隔离、权限失败、并发冲突，以及 GitHub 成功但通知失败后的单独重试。
- 验收以目标分支实际出现正确文件、消息实际到达为准，预览或创建了未挂到分支的提交对象不算完成。
