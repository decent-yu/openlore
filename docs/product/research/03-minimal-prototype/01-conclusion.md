# 最小原型：RSS 订阅与文章导入

日期：2026-10-15。依据：[来源配置](../../feature/01-source-configuration.md)、[采集能力](../../feature/02-content-collection.md)、[内容处理](../../feature/03-content-processing.md)、[推送与 Git 沉淀](../../feature/04-delivery-and-git-archive.md)。

## 结论

**首期采用两个采集入口：RSS/Atom 订阅、单篇 URL 导入。首批自动来源确定为 Cloudflare Blog 和 Simon Willison，默认关注 Agent 工程与深度工程实践。**管理员维护公共来源，用户建立多个采集组；两个入口共用正文提取能力，各组按自己的筛选条件生成摘要，并使用各自的推送与 Git 目标。

对当前这些公开技术网站，标准订阅与直接 HTTP 获取更适合建立可重复验证的基线。AI 负责理解主题、判断文章相关性和生成摘要；采集路径由配置明确指定。AI 浏览器与多平台 skill 留作后续复杂来源的候选。

首期来源方向已确认，具体能力边界以 [feature 总览](../../feature/index.md) 及其关联接入设计为准；整体技术选型仍待编码验证，尚未实现四项功能。

Cloudflare 提供厂商一手工程实践，Simon Willison 补充 LLM 与 Agent 的独立实践分析，两者共同覆盖当前阅读目标。Jules Blom 保留为前端专题候选，Anthropic Engineering 作为后续 Agent 深度内容候选。

各网站的主要内容、采集入口、验证结果与边界见[网站信息源清单](02-web-source-catalog.md)，来源配置要求见 [feature 01](../../feature/01-source-configuration.md)。已完成的验证仅说明当时可读取，不代表长期稳定性或正文完整度已验收。

## 配置如何驱动采集

配置分为两层：**管理员配置可用来源与采集入口，用户配置采集组、逐来源关键词及同步目标。**来源说明中的适合主题用于辅助选择，用户的关注方向由采集组表达。

| 层次 | 示例 |
| --- | --- |
| 公共来源 | Cloudflare Blog、Simon Willison；管理员维护说明、RSS 地址、启用状态和处理范围 |
| 采集组：Agent 相关知识 | 选择两个来源，分别设置 Agent 关键词；同步到该组指定 Git 仓库的 `knowledge/agents/` 与 Webhook A |
| 采集组：后端性能优化 | 选择 Cloudflare，设置数据库和性能关键词；同步到该组指定 Git 仓库的 `knowledge/performance/` 与 Webhook B |

两组可以复用来源，也可以配置不同仓库。字段与交互以 [feature 01](../../feature/01-source-configuration.md) 为准，此处不预设数据结构和实现界面。

首轮的时间窗与处理上限由管理员维护的采集设置控制；手动配置的单篇文章入口不受新文章时间窗限制。候选被上限截断时明确报告，关键词筛选由内容处理环节执行。

## 四项功能的最小交付

| 功能 | 首版范围 | 用户能看到的结果 |
| --- | --- | --- |
| 来源配置 | 管理员维护来源说明与入口；用户创建多个采集组，设置逐来源关键词和同步目标 | 用户可理解来源内容，按组独立配置关注方向与去向 |
| 采集能力 | RSS 解析；文章 HTTP 获取；跟随重定向；逐条检查发布时间与 ID；保存内容和逐来源状态 | 列出新增、重复、补抓成功、失败及原因 |
| 内容处理 | 正文清洗、规范 URL、源内 ID 与规范 URL 去重；一个模型按各组关注方向及来源关键词生成中文短摘要和匹配理由 | 每条结果附标题、原文、来源、日期、摘要、所属采集组与完整度 |
| 推送与 Git 沉淀 | 各组结果生成 Markdown，按组配置的 Webhook、Git 仓库和路径交付 | 同一组的群简报与仓库归档对应同一批次，各组分别记录结果 |

首版按“一次手动运行”验证采集组的完整闭环；跑通后再由外部定时器触发。使用轻量持久状态记录采集、处理和交付结果，使同一批任务可以重跑。

## 技术取舍

建议单进程工具起步：Python + [feedparser](https://feedparser.readthedocs.io/en/latest/) 解析订阅，HTTP 客户端请求页面，[Trafilatura](https://trafilatura.readthedocs.io/en/latest/) 提取正文，SQLite 保存条目与状态，再接一个模型和文件同步能力。两个采集能力独立成目录，通过[统一采集接口](../../../design/collection-adapters.md)接入；按组输出的文件包通过[GitHub 同步接口](../../../design/processing-and-delivery.md)新增或更新目标仓库文件。

- 先检查 Feed 内容是全文还是摘要；需要时再补抓，保留原始链接和最终链接。
- RSS/Atom 中的 ID 用于源内识别；重定向后的规范 URL 用于合并重复导入。内容 hash 用于识别已存在文章是否改变。
- 以条目是否可靠入库为准推进状态；正文失败允许单独补抓。ETag/Last-Modified 用于减少重复下载，不替代条目去重。
- 模型只基于取得的内容判断和总结，输出结构化结果；抓取失败、正文缺失或模型失败单独记录并可重试。
- 群推送与 Git 分别保存状态；一端失败只补做该端。发送结果不明时单独标记，不承诺没有幂等支持的渠道绝对零重复。

库与结构属于建议，产品行为不绑定特定语言。重点是同一套流程能可靠处理两个入口，而不是首版就覆盖更多平台。

## 跑通的验收标准

1. 从 Cloudflare 与 Simon Willison 的 Feed 发现候选；给定文章 URL 能单独导入，重复导入与 RSS 命中合并为同一条。
2. 入选内容有可核对的正文、来源链接、主题匹配理由和短摘要；图示未读、摘要不完整等情况可见。
3. 连续运行两次，同一组内相同且未变化的内容不重复进入新简报；已有条目变化可更新记录，不影响其他组独立处理。
4. 模拟一个来源超时，其余来源继续完成；恢复后可补抓失败条目，不重复处理已成功条目。
5. 创建两个采集组，至少复用一个来源并设置不同关键词及同步目标，结果按组独立筛选。每组均按自己的 Git 仓库、路径与 Webhook 完成真实交付，修改一组不影响另一组。

**首期方向收敛为两个公共信息源、可独立配置的多个采集组和四项功能闭环。**输入输出、能力目录与 GitHub 文件更新流程已进入功能及设计文档；模型提供者与具体 Webhook 平台在实施前确定。
