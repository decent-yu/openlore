# AI 主导的信息采集：方案与建议

日期：2026-10-15。参考：[产品规划](../../product-brief.md)、[上一批采集调研](../01-open-source-projects/02-source-collection.md)。本次聚焦采集能力。

## 初步结论

**可以先让 AI 工具配合 skills 完成采集验证，不必先建设完整的爬虫平台。**较适合 OpenLore 的分工是：AI 识别来源、选择工具、处理异常和检查内容；CLI/API/浏览器负责实际读取；小型脚本保存游标、去重和运行结果。

已有 skill 能读取公众号文章、X 帖子、RSS 和网页，也有主题搜索与持续监测方案。但“能读链接”“能搜索相关信息”“能完整追踪指定账号”是不同能力。尤其公众号账号文章列表的持续发现，不能由单篇阅读 skill 自动解决。

本次核查官方文档、skill 指令、关键源码及用户修复记录；用一个公开 RSS skill 脚本做了小样本运行。未安装新 skill，未验证 X/公众号登录态，也未调用付费采集服务。具体依据见：

- [工具与 skills](02-tools-and-skills.md)：候选能力、依赖、限制与安装入口。
- [公开实践与验证结果](03-public-practices.md)：实际实现、用户踩坑及可借鉴做法。

## 可选技术路线

| 路线 | AI 负责什么 | 适用场景 | 主要边界 |
| --- | --- | --- | --- |
| 搜索型 Agent | 拆问题、搜索、读原文、追查线索 | 发现新项目、收集某项技术的近期讨论 | 搜索召回与索引时效不等于指定来源的完整更新；参考 last30days |
| Skill + CLI/MCP | 根据来源选择读取工具，检查结果并补抓 | 指定来源与已知链接，快速验证多平台能力 | Skill 是操作流程，仍依赖工具、网络与凭据；参考 Agent-Reach、x-reader |
| 浏览器 Agent | 看页面、点击、翻页、滚动、处理动态内容 | 没有 API/RSS，或直接抓取拿不到正文 | 分页终止、登录失效与覆盖范围需明确；参考 agent-browser、Browser Use |
| 托管采集与监测 | 提供目标和提取结构，调用采集服务 | 希望少维护浏览器，采集公开站点与文档 | Firecrawl 的抓取、监测和 Agent 能力分别核实；云服务按调用消耗资源 |
| AI 辅助生成固定采集规则 | 首次理解页面，生成和修正提取规则 | 页面结构稳定、需要重复采集的网站 | Crawl4AI 支持生成 CSS/XPath schema 后重复执行；页面变化仍需检测 |

以上是依据 [02 工具核查](02-tools-and-skills.md) 的方案归纳，不是性能排名。纯浏览器逐页探索适合接入与疑难处理；稳定来源可固化为脚本，减少每轮重新探索。

## 按来源组合

| 来源 | 发现新内容 | 读取正文 | 对本项目的建议 |
| --- | --- | --- | --- |
| 技术网站、博客 | RSS、网站列表页；搜索补充发现 | Jina Reader、Firecrawl、Crawl4AI；必要时浏览器 | 优先验证公开网页，是最容易建立基线的来源 |
| GitHub 项目 | 官方 API/CLI 获取 Releases 等事件 | 发布说明、README、关联文档 | AI 可直接调 `gh`，不需要先让浏览器遍历仓库 |
| X 账号 | 账号时间线工具；主题搜索另作补充 | x-reader、平台 CLI、baoyu-url-to-markdown，必要时登录浏览器 | 分开验收列表、长文、引用帖和线程，不能用搜索结果数量代表账号完整性 |
| 公众号 | 沿用上一批 WeRSS 等列表接入候选，或人工提供链接 | x-reader 的微信读取链路；浏览器补充验证 | 先证明正文读取，再验证账号新文章发现；搜索只能作为补充入口 |

## 建议先验证的最小组合

1. **一份项目采集 skill**：暂称 `openlore-collect`，描述来源配置、工具选择、失败回退和输出格式；本次仅提出方案。
2. **稳定入口**：RSS 解析器 + GitHub CLI/API，保留原文 ID、URL、时间与更新位置。
3. **多平台正文读取**：优先对照测试 x-reader 与 baoyu-url-to-markdown；公众号、X 各准备真实链接。
4. **浏览器兜底**：复用现有浏览器能力，或在 agent-browser / Browser Use 中选一个。需要更多平台接入时再试 Agent-Reach。
5. **可选服务**：如果本地维护成本高，再对比 Firecrawl；需要大量固定站点规则时再引入 Crawl4AI。

这些工具功能有重叠，不需要一次装齐。已有宿主模型可以负责判断与总结，但“无需额外模型 API Key”不等于模型调用、浏览器或数据服务没有成本。

## 一次采集必须交付什么

- **逐来源结果**：成功、部分成功或失败，实际覆盖的时间窗口、条目数、是否还有下一页。
- **逐条内容**：原始 URL、来源与上游 ID、作者、发布时间、发现时间、正文、附件与实际读取方式。
- **证据完整度**：全文、摘要、正文缺失、附件未读等明确状态；保留失败原因，不让模型补写抓不到的内容。
- **可恢复状态**：保存已抓条目与游标，只在对应数据可靠落盘后推进；正文补抓与列表发现分开处理。

规则应由脚本做必要校验，AI 负责解释和处理复杂异常。网页和帖子中的文本作为待分析数据，不作为执行指令。

## 如何判断这条路线值得继续

先做“已知链接读取”，再做“来源增量发现”，最后连续运行一周：

| 阶段 | 样本 | 看什么 |
| --- | --- | --- |
| 正文读取 | 普通文章、公众号、X 长文/引用帖、动态网页 | 原文是否对应，正文有无截断，代码/图片/附件是否丢失，验证页是否误报成功 |
| 增量发现 | 每类选 2–3 个真实来源，人工建立同一时间窗的条目清单 | 发现率、分页覆盖、重复率、更新延迟；没有对照清单就不宣称完整采集 |
| 持续运行 | 重跑、单源超时、登录失效、正文补抓 | 是否丢游标、是否重复入库、恢复是否可控、每条有效内容的耗时与成本 |

建议先以 x-reader 的“内容完整度报告”和 Agent-Reach 的“按平台选择工具”作为设计参考。OpenLore 自己掌握来源清单、持久状态与验收，便于以后替换采集工具。
