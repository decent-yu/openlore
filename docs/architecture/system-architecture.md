# 系统架构：云端控制服务与 AI Runner

核对日期：2026-10-17。部署主线是 **云端控制服务编排任务，独立 Runner 在执行机器上运行 AI CLI**。现有代码已支持这个运行边界；独立分发、设备管理和重启恢复仍需完善。

## 部署角色

| 角色         | 负责                                                                              | 常驻进程与依赖                                            |
| ------------ | --------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 云端控制服务 | 网站/API、来源采集、内容池、计划、流水线推进、AI 任务队列、结果校验、归档和群推送 | 一个 Node 服务；Python 解析环境；本机 SQLite 与文件存储   |
| AI Runner    | 主动连接控制服务、领取指定任务、同步 Skill、调用 AI CLI、回传结果与产物           | 独立 `worker` 进程；Node、已安装并登录的 Codex/Gemini CLI |
| 浏览器       | 配置计划、查看状态、阅读成果、触发操作                                            | 访问云端网站；关闭页面不停止任务                          |

Runner 不运行网站、采集器或调度器，不共享云端数据库，也不需要 `npm run dev`。AI 账号和用户 CLI 配置留在执行机；GitHub Token、通知 Webhook 与业务数据库由控制服务管理。Runner 返回的材料和产物经云端校验后，由云端完成外部交付。

“云端”是部署角色，也可放在自己的常驻服务器。同一电脑可同时运行控制服务和独立 Runner 调试，职责边界不变。当前控制服务按**单实例**运行：多个 Runner 不要求引入 Redis 或共享数据库，也不代表控制服务已支持多副本。

## 业务流与任务流

1. 云端定时或手动采集来源；Python 子进程解析材料，准入后的文章进入内容池。
2. 云端根据流水线配置确定审核/调研阶段，生成包含 Prompt、材料、Skill 版本和输出约束的 AI 请求，写入持久 AI 队列。
3. Runner 通过出站 HTTPS 拉取配置、报告心跳并请求任务；云端按绑定的执行器配置和并发限制授予任务租约。
4. Runner 在独立目录准备输入与 Skill，按需启动 AI CLI；执行期间续租，完成后提交结构化结果和 `output/` 产物。
5. 云端验证身份、租约与结果，保存调用记录并推进流水线；文章和调研文件由云端归档到 GitHub，成功结果供首页和汇报方案使用。汇报由云端按可配置模板直接渲染，不经过 AI Runner。

“云端分发”指调度权、任务状态和结果接纳由云端掌握；传输使用 Runner 主动拉取即可，无需云端直接连接用户电脑。当前采用短轮询，尚未使用长轮询或 WebSocket。

## 当前实现与设计缺口

| 能力           | 当前实现                                                                          | 确定的改进方向（待实现）                                                       |
| -------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 独立运行       | `node apps/server/dist/cli/index.js worker <配对文件>`，不启动 HTTP 服务          | Runner 独立入口、安装包与发布流程；避免用户克隆和构建服务端依赖                |
| 调度与设备身份 | `ai_profiles` 同时绑定模型配置、连接方式和 Worker 令牌；`ai_jobs.profile_id` 路由 | 拆分模型配置与 Runner 设备注册，明确任务约束与设备能力                         |
| 多机器与并发   | 不同配置可接入不同 Worker；同一配置的领取受云端并发上限约束                       | 设备级在线状态、容量、标签匹配和设备撤销；现有一个配置的单一心跳不能表达设备池 |
| 配对与权限     | 专用长效令牌，服务端保存哈希；重新配对使旧令牌失效                                | 一次性配对凭证换设备身份、协议/版本握手与更细权限                              |
| 排队与租约     | SQLite AI 队列、超时、续租、失联重领、过期结果拒收                                | 持久化阶段推进和交付幂等；不能承诺 AI 执行恰好一次                             |
| 控制服务重启   | 取消在途 AI 队列任务，运行中流水线失败；内存中的等待与业务协程不恢复              | 以持久阶段状态重建推进器，恢复排队任务，核对运行租约后决定重试                 |
| 日志与取消     | 结果回传时保存诊断；续租无效后停止执行                                            | 增量日志/进度协议、显式取消与取消确认、可重试产物上传                          |
| 生命周期       | 手动启动；`service` 仍是占位                                                      | 独立 Runner 的安装、升级、启动、停止和系统服务管理                             |
| 本机与 SSH     | `local` 由后端直接调用；`ssh` 由后端连接远端执行                                  | 保留为开发/受管机器辅助方式，正式用户接入主线使用 Runner                       |

以上是架构设计与差距清单，本次文档调整没有实现这些待办，也没有新增 `runner`、`runner install` 等命令。当前命令和配对字段仍使用 `worker`，文档称其部署角色为 Runner。

## 交付顺序与验收

1. **分发与握手**：独立 Runner 制品、最小依赖、协议版本、设备注册与撤销。新电脑只安装 Runner 和 AI CLI 即可上线。
2. **可靠推进**：持久化阶段状态、结果与交付幂等、服务端重启核对、显式取消。重启、断网、结果重复投递都有明确终态；过期执行不能覆盖有效结果。
3. **可运维性**：设备状态、增量日志、诊断、系统常驻与升级流程。电脑休眠后界面能区分离线、排队和运行超时。
