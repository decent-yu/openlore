# AI Runner 协议与生命周期

本文记录当前 `worker` 的实现，部署角色统称 Runner。系统拓扑见[整体架构与 SVG](system-architecture.md)，安装配对见[操作指引](../guides/ai-executors.md)。

## 独立启动边界

`cli/index.ts` 仅在 `serve` 分支动态导入控制服务、数据库和调度模块。`worker` 分支运行 `modules/executors/worker.ts`，经 HTTPS 连接已有控制服务；不监听网站端口、不初始化业务数据库、不运行采集器。

当前共享的是源码包和构建依赖，尚无独立 Runner 发行包。`local` 和 `ssh` 调用同一个工作区执行程序，但不经过 Worker 领取协议。

## 配对与身份

云端为 `ai_profiles` 生成随机专用令牌，仅保存 SHA-256 哈希；配对 JSON 保存 `server_url`、`profile_id`、`token`、`name`。可选 `cli_path` 和 `overrides` 覆盖执行机配置。远程 URL 要求 HTTPS，回环地址允许 HTTP。

当前令牌长期有效，直到重新配对或删除配置。重新配对会清除在线时间、替换令牌哈希，并取消该配置排队与运行中的 AI 任务。它还不是“一次性注册码换设备证书”的设备注册协议；管理令牌与 Worker 令牌不能混用。

## HTTP 交互

统一前缀 `/api/v1/worker/:id`，每次校验对应配置的 Bearer 令牌。

| 接口                     | 调用者 | 行为                                                   |
| ------------------------ | ------ | ------------------------------------------------------ |
| `GET /configuration`     | Runner | 获取模型提供方、CLI 路径及执行配置                     |
| `POST /heartbeat`        | Runner | 报告名称和本地 Skill 清单                              |
| `POST /claim`            | Runner | 原子领取该配置队列中的一个任务，受并发上限约束         |
| `POST /jobs/:job/renew`  | Runner | 续租并确认任务仍有效，同时回传最新执行日志快照         |
| `POST /jobs/:job/result` | Runner | 提交结构化结果、诊断、产物；过期或不匹配的租约返回 409 |

Runner 空闲循环约 2 秒一次，每约 10 秒更新配置和心跳；单请求网络超时为 15 秒。没有任务时返回空结果，当前不是长轮询。页面以最近 45 秒内心跳判断在线；在线仅代表通信及 CLI `--version` 检查通过，不代表模型登录或额度有效。

## 排队、执行与结果

- `ai_jobs` 保存请求、`profile_id`、状态、租约、尝试次数、结果和 deadline。
- 状态为 `queued → running → completed`；`completed` 表示结果已经回传，AI 业务成功与否另看 `ExecutionResult.status`。取消、过期和领取失败还有 `cancelled`、`expired`、`failed` 终态。
- 领取时授予 60 秒租约；执行期间约每 10 秒续租。失去有效租约立即请求终止 AI 进程；续租网络持续失败超过约 40 秒也终止。
- 领取逻辑将过期租约重新入队，达到三次领取尝试后失败。回传时再次核验配置、租约、任务状态和期限，拒收旧执行结果。可能出现重复执行，但不能接受过期结果覆盖有效结果。
- 云端当前以每 500ms 查询结果的内存协程等待；排队上限单独计算，总 deadline 为入队时间加排队上限和执行上限。AI CLI 自身还有执行机上的单次超时。
- 本机与 SSH 在控制服务进程内按执行器 ID 共用并发槽位，审核、修正、调研和备用接管不能各自绕过限制；超出并发时等待队列，超出排队时限明确失败。Worker 仍通过数据库租约队列限制并发。初审业务按主执行器并发补充工作，不再全局逐篇等待。
- 日志区分等待槽位与 CLI 执行，单次 900 秒从 CLI 启动计时，不把排队时间挤占为执行时间；Worker 排队耗时取服务端观察到任务转入运行时的时间。
- 本机执行与 SSH 实时回传日志，Worker 在约每 10 秒续租时上传最新快照；云端仅接受有效租约的进度，重领后清空旧快照。调用详情默认打开“执行与实时日志”，运行中每 2 秒刷新，显示最近进程输出时间。没有输出不能推断为模型正在推理。
- Gemini 使用 `stream-json` 保留工具调用、工具结果和最终完成事件；只有最终成功事件及有效业务结果才算完成。仍按原流程加载 Skill、读取工作区文件，不把正文内嵌为 Prompt，也不关闭 CLI 安全检查。
- 产物和完整诊断随最终结果 JSON 回传；尚无分块产物上传或本地持久回传队列。网络失败时回传最多尝试五次，耗尽后不能保证产物送达。

## 执行失败与诊断

- 初审、选文与调研统一使用执行器配置的时限，默认 900 秒，不设初审专属超时。
- 明确的 Schema 无效或 Gemini 内部策略检查服务失败会结束当前尝试，按原顺序切换备用执行器，不等待剩余时限。普通模型 429 允许 CLI 在统一时限内自行重试；恢复成功不会因历史限流日志被误判失败。所有执行器失败时保留每次失败原因。
- Gemini 的 `Policy generation/enforcement failed` 与 `429 RESOURCE_EXHAUSTED` 同时出现时，标记为内部策略检查服务限流；这不能证明主模型或整个账号额度耗尽。普通模型 429 单独显示为请求限流或模型暂不可用。
- 不自动放宽读文件权限、不切换到 YOLO，也不修改执行机的全局配置。工具拒绝执行的细节保留在日志中，供检查对应 CLI 策略与授权。
- Codex 结构化输出的每一层对象明确设置 `additionalProperties: false`；初审及嵌套选文结构均有回归校验。规范见 [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。Gemini 事件格式见[官方 Headless 文档](https://geminicli.com/docs/cli/headless/)。

工作区运行中写入 `events.log` 和 `stderr.log`。服务器对日志快照做凭据脱敏；实时 stdout/stderr 各保留末尾 64KB，最终诊断各保留末尾 512KB，超出部分标记截断。文件内容仍属于执行机本地原始诊断，分享前需核查敏感信息。

## 故障语义

| 场景                     | 当前行为                                                                           |
| ------------------------ | ---------------------------------------------------------------------------------- |
| Runner 尚未上线          | 云端等待任务被领取，达到排队上限后失败；不回退到浏览器执行                         |
| 执行机断网、休眠或退出   | 停止心跳；租约失效后可重领，仍受尝试次数与 deadline 限制                           |
| 控制服务重启             | `serve` 启动时把在途 AI 任务取消、运行中流水线标记失败，调用日志标记中断；需要重跑 |
| 结果晚到或重复回传       | 无有效租约则拒收，不推进业务                                                       |
| Worker 令牌失效          | 停止连接并提示重新配对                                                             |
| 重新配对或服务端取消租约 | Runner 在下一次续租发现无效后终止，传播不是瞬时完成                                |

当前没有完整的用户取消、跨重启恢复与恰好一次交付协议。改进顺序见[架构差距与验收](system-architecture.md#交付顺序与验收)。

## 工作区与材料

### 校验修正与会话

初审验证在同一业务调用内进行：原结果不合格时，保留原始输出和逐项错误，最多追加一次校验修正。修正使用明确的 CLI 会话 ID 和原工作区，Gemini 使用 `--resume <id>`，Codex 使用 `exec resume <id>`；不使用 `latest/--last`。首次 Codex 执行保存会话，不再使用 `--ephemeral`。

会话句柄绑定 Job、文章 ID、材料、Skill 版本、执行器配置和输出 Schema；执行机核对私有会话记录、正文与 Skill 文件，拒绝跨任务、材料变化、目录越界、符号链接和同工作区并发执行。句柄随 Worker/SSH 请求及结果传递，不能把不同机器的路径当作可迁移会话。会话丢失明确失败，不悄悄重新初审；执行异常需要备用接管时，备用执行器接收已有结果和错误，明确记录为新的执行器尝试。

调用日志保存首次执行与修正的独立输出、错误、会话 ID 和耗时，但以同一个 Job 汇总。工作区 `prompt.txt` 保留最初任务，`correction-prompt.txt` 保存修正要求。CLI 自身的会话历史由对应 CLI 管理，工作区 7 天清理不等于清理 CLI 全局会话库。当前续聊用于在途业务修正，不承诺服务重启后的自动续跑。

每个新业务执行独立创建 `<workspace_root>/jobs/job-*/`，校验修正复用该工作区，包含 `.agents/skills/`、`input/article.md`、`output/`、`prompt.txt`、`manifest.json` 等。Skill 包按哈希和路径校验，不安装到全局目录。

同步模式传入服务器管理的 Skill 版本；本地模式由执行机读取配置目录，并检查已选版本。默认保留完成目录 7 天，清理由后续任务启动时触发；不是独立定时清理服务。

AI CLI 环境移除 `OPENLORE_*`，沿用执行机的模型授权与其他用户环境；这不等于完整环境隔离。任务目录是文件组织边界，不是操作系统隔离。控制服务负责保存校验后的结果与执行日志；执行机不需要知识库写入或群通知凭据。仓库研读在控制服务和执行机复用本地 Git 缓存，私有源码需要各机器自身的 Git 读取权限。每次新研究更新真实默认分支后传递实际 Commit，执行机按该快照研究并核对源码完整性和行号证据；归档重试复用已有结果。
