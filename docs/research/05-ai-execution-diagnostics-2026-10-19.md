# AI 执行耗时与重试问题核查

核查日期：2026-10-19，时区 Asia/Shanghai。范围：真实 Gemini CLI 对照实测、调用日志、初审校验与执行生命周期。本文是后续统一修复的依据，不代表已实施新方案。

## 结论

同题任务绕过 OpenLore 直接调用 Gemini，运行 **772.693 秒（12 分 52.693 秒）**仍未返回评分；按用户“先修项目、Gemini 后续确认”的指示结束自建对照进程。首次工具请求发生在 **372.683 秒**，两次相对路径读取均被策略拒绝。另一次仅回复 OK 的短问答用时 **55.271 秒**；原业务的备用 Codex 则用 **36.302 秒**完成材料不足的审核结论。

已在直接 CLI 路径复现长等待，不能将所有耗时归为 OpenLore 后端调度；也不能据此宣称 Gemini 模型能力需要十几分钟，或已定位 Gemini 工具本身的缺陷。环境/网络/策略原因留待确认，项目内已复现的校验和重试缺陷先行修复。

已确认存在两条相互放大的问题链：

1. 执行机的 Gemini 请求等待、工具策略拒绝和网络异常拖慢单次执行。
2. OpenLore 在材料质量、引用校验、会话续用和重试归属方面的实现缺陷，导致已产生有用结果后重新执行整轮任务。

保留工作区文件与 Skill 加载方式，统一使用执行器配置的 900 秒默认时限。本轮只记录与实测，不修改业务代码、全局 CLI 配置或正在运行的用户任务。

- 命令参数与当前 Gemini 执行器一致：`gemini -p "<原 Prompt>" --output-format stream-json --approval-mode auto_edit --skip-trust`。
- 模型仍为 `auto`，沿用当前用户授权及 CLI 配置；没有关闭策略检查、遥测或 Hooks，没有使用 YOLO。

- 进程时限同为 900 秒。逐条记录事件到达时间，并区分初始化、首次工具、首次回答、完成事件、进程退出。

### 解释边界

每个直接 CLI 场景仅执行一次，不是性能分位统计。同题实测前半段与原业务证据重试重叠；短问答与同题实测重叠，未隔离账号并发或服务路由影响。因此可以确认“直接 CLI 也会长时间无进展”，但无法把场景间的时差全部归因于工具调用、Hook 或某个模型。

本轮同时增加“请仅回复 OK，不调用任何工具”的短问答，只测试同一 CLI 的启动和基础响应，不代替文章审核，也没有将文章正文内嵌到 Prompt。短问答首个回答为 54.150 秒，进程结束为 55.271 秒；没有工具调用，最终回复 `OK`。CLI 统计输入 13,244、输出 45、总量 14,212，含自动路由模型；这些累计字段不用于直接推算费用。

即使直接调用也慢，也不能证明审核这篇文章在业务上“需要十几分钟”。网络等待、模型路由、工具权限检查、内部重试和遥测都属于执行开销。首个工具事件前的空档不能直接命名为“模型推理时间”；导出超时不能当成主模型额度不足。

本轮沿用同一 CLI 配置，能够检查“绕过 OpenLore 是否仍慢”，不能单独识别代理、模型路由、某条 Hook 或遥测配置各贡献多少。后续应一次只改变一个条件，并记录更多样本及 p50/p95，不用单次结果承诺正常耗时。

## 引用校验复现

调用模型时，`assessmentMaterial()` 将 `Metadata`、`Title` 和原始正文包装为一个文件；业务校验却只把未包装的原始正文传给 `hasGroundedEvidence()`。

本例原正文 **555 字符**，发给模型的材料 **653 字符**。本轮未重新访问来源网页，不能断定原站本身缺正文还是采集器漏抽，但现有材料确实不足以评估该发布。使用当前项目函数只读复现结果如下：

| 模型引用                                                                 | 在发给模型的材料中 | 在原始正文中 | 校验结果 |
| ------------------------------------------------------------------------ | ------------------ | ------------ | -------- |
| `Title: Release: llm-tools-datasette 0.1.1`                              | 存在               | 不存在       | 失败     |
| `Hello Python 3.15...` 的原始 Markdown 列表行                            | 存在               | 存在         | 通过     |
| `We're going to need default hard budget caps...` 的原始 Markdown 列表行 | 存在               | 存在         | 通过     |

三条引用在实际材料中全部可找到；对原始正文检查时，只有标题引用失败。校验使用 `every()`，一条失败即否定整个结果。

这不是放开标题、导航作为技术证据的理由：两条导航文字虽然能逐字匹配，也不代表目标文章有实质内容。需要统一材料边界与来源分段，支持材料不足的业务结果，并返回具体校验错误。

## 当前执行机环境快照

只读核查 `~/.gemini/settings.json`：ConSeca 开启，遥测开启，使用远程 OTLP gRPC Collector，`logPrompts=false`；SessionStart、BeforeAgent、AfterAgent、BeforeTool、AfterTool、SessionEnd 均有配置。Hook 脚本来自 Orca、Superset 与 ai-otel，其中 ai-otel 的一条 SessionStart 定义格式不合法，被 CLI 跳过。

## 后续统一修复顺序

1. 固定本例，先修材料边界、缺失正文状态和结构化校验反馈，避免无收益重试。
