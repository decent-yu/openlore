## 结论

**首期采用两个采集入口：RSS/Atom 订阅、单篇 URL 导入。首批自动来源确定为 Cloudflare Blog 和 Simon Willison，默认关注 Agent 工程与深度工程实践。**工作区先配置仓库连接与本地 AI，管理员维护公共来源，用户建立多个采集组并配置路由；两个入口共用正文提取能力，各组按自己的筛选条件生成摘要，并使用各自的推送与 Git 目标。

对当前这些公开技术网站，标准订阅与直接 HTTP 获取更适合建立可重复验证的基线。AI 负责理解主题、判断文章相关性和生成摘要；采集路径由配置明确指定。AI 浏览器与多平台 skill 留作后续复杂来源的候选。

阅读产物现按日期批次与文章组织，文章旁保存 assets，可选简报和逐篇调研由组规则勾选；具体以 feature 03/04 为准。

首期来源方向已确认，具体能力边界以 [feature 总览](../../product/feature/index.md) 及其关联接入设计为准；整体技术选型已确定，待编码验证，尚未实现四项功能。

## 配置如何驱动采集

配置分为两层：**管理员配置可用来源与采集入口，用户配置采集组、逐来源关键词及同步目标。**来源说明中的适合主题用于辅助选择，用户的关注方向由采集组表达。

| 层次 | 示例 |
| --- | --- |
| 公共来源 | Cloudflare Blog、Simon Willison；管理员维护说明、RSS 地址、启用状态和处理范围 |
| 采集组：Agent 相关知识 | 选择两个来源，分别设置 Agent 关键词；同步到该组指定 Git 仓库的 `knowledge/agents/` 与 Webhook A |
| 采集组：后端性能优化 | 选择 Cloudflare，设置数据库和性能关键词；同步到该组指定 Git 仓库的 `knowledge/performance/` 与 Webhook B |

两组可以复用来源，也可以配置不同仓库。字段与交互以 [feature 01](../../product/feature/01-source-management.md) 为准，当前连接复用、页面和运行规则以功能文档为准。

当前组默认首次回看 7 天、每批评估 20 篇、入选最多 10 篇；管理员控制来源轮询预算。手动导入文章可超出时间窗。详细候选与关键词规则统一维护在 feature 02/03。

## 四项功能的最小交付

| 功能 | 首版范围 | 用户能看到的结果 |
| --- | --- | --- |
| 来源配置 | 管理员维护来源说明与入口；用户创建多个采集组，设置逐来源关键词和同步目标 | 用户可理解来源内容，按组独立配置关注方向与去向 |
| 采集能力 | RSS 解析；文章 HTTP 获取；跟随重定向；逐条检查发布时间与 ID；保存内容和逐来源状态 | 列出新增、重复、补抓成功、失败及原因 |
| 内容处理 | 正文清洗、规范 URL、源内 ID 与规范 URL 去重；一个模型按各组关注方向及来源关键词生成中文短摘要和匹配理由 | 每条结果附标题、原文、来源、日期、摘要、所属采集组与完整度 |
| 推送与 Git 沉淀 | 各组结果生成 Markdown，按组配置的 Webhook、Git 仓库和路径交付 | 同一组的群简报与仓库归档对应同一批次，各组分别记录结果 |

本期建设本地常驻服务、来源轮询与组运行计划，先手动验收闭环，再启用自动任务。持久队列支持中断恢复；本地 Codex/Gemini 与深度调研见当前 feature 03。

## 技术取舍

实施基线以[架构选型](../../architecture/technology-stack.md)为准：Node.js 主服务负责 HTTP 获取、编排和 SQLite 状态，Python 子进程通过 feedparser 解析订阅、Trafilatura 提取正文，前端采用 React + shadcn/ui。采集能力通过[内容源管理](../../product/feature/01-source-management.md)统一接入；按组输出的文件包通过[Git 交付归档](../../product/feature/05-git-delivery-and-archive.md)同步至目标仓库。

- 先检查 Feed 内容是全文还是摘要；需要时再补抓，保留原始链接和最终链接。
- RSS/Atom 中的 ID 用于源内识别；重定向后的规范 URL 用于合并重复导入。内容 hash 用于识别已存在文章是否改变。
- 以条目是否可靠入库为准推进状态；正文失败允许单独补抓。ETag/Last-Modified 用于减少重复下载，不替代条目去重。
- 模型只基于取得的内容判断和总结，输出结构化结果；抓取失败、正文缺失或模型失败单独记录并可重试。
- 群推送与 Git 分别保存状态；一端失败只补做该端。发送结果不明时单独标记，不承诺没有幂等支持的渠道绝对零重复。

语言与工程边界已在架构选型中确定，产品行为通过统一协议约束。重点是同一套流程能可靠处理两个入口，而不是首版就覆盖更多平台。

## 跑通的验收标准

1. 从 Cloudflare 与 Simon Willison 的 Feed 发现候选；给定文章 URL 能单独导入，重复导入与 RSS 命中合并为同一条。
2. 入选内容有可核对的正文、来源链接、主题匹配理由和短摘要；图示未读、摘要不完整等情况可见。
3. 连续运行两次，同一组内相同且未变化的内容不重复进入新简报；已有条目变化可更新记录，不影响其他组独立处理。
4. 模拟一个来源超时，其余来源继续完成；恢复后可补抓失败条目，不重复处理已成功条目。
5. 创建两个采集组，至少复用一个来源并设置不同关键词及同步目标，结果按组独立筛选。每组均按自己的 Git 仓库、路径与 Webhook 完成真实交付，修改一组不影响另一组。

**首期方向收敛为两个公共信息源、可独立配置的多个采集组和四项功能闭环。**输入输出、能力目录与 GitHub 文件更新流程已进入功能及设计文档；当前已明确 Codex/Gemini CLI 双适配与通用 JSON Webhook，工作区连接和详细默认行为以最新 feature 文档为准。
