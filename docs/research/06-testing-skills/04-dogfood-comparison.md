# Vercel 与 Every：异同和能力边界

核查：2026-11-10；基于[源码拆解](03-dogfood-core-logic.md)，表内机制是源码事实，收益和风险是分析判断，尚无端到端效果对照。

**Vercel 更适合“给个网站，帮我找问题”；Every 更适合“这次代码改动能否交付”。两者可以组合，但覆盖目标和通过判据必须先统一。**

## 1. 逐项比较

| 维度 | Vercel dogfood | Every ce-dogfood |
| --- | --- | --- |
| 最小输入 | URL | PR、分支或当前分支，外加项目上下文 |
| 范围来源 | 用户指定范围及运行中的页面 | Git 改动及可能影响的相邻用户旅程 |
| 测试视角 | 黑盒，禁止读取被测应用源码 | 读取源码差异，随后以真实浏览器验证 |
| 测什么 | 由导航、交互及缺陷分类清单引导探索 | 先画旅程图，再从节点与分支推导矩阵 |
| 正确性依据 | 页面反馈、常识、用户给定目标 | 代码上下文、产品愿景、人物画像、适用规则包和运行反馈 |
| 浏览器 | 固定使用直接调用的 agent-browser | 能覆盖矩阵时优先宿主内置浏览器，否则 agent-browser；一轮只用一套 |
| 取证要求 | 行为问题视频 + 逐步截图；静态问题单图 | 截图、控制台、逐场景结果；未统一强制每个缺陷录视频 |
| 自动修复 | 未定义修复阶段，以问题交付为主 | 小且明确的问题自动修复，复杂决策转人工 |
| 回归证明 | 不要求生成自动化测试 | 行为缺陷默认补自动化回归；纯视觉可说明理由后用截图/浏览器复查 |
| 状态与恢复 | 发现即写缺陷，未定义完整场景状态机 | 矩阵作持久检查点，恢复未完场景，保留终态阻塞 |
| 完成标准 | 目标是约 5–10 个有充分证据的问题，再汇总 | 所有场景进入规定状态，记录自动化套件结果及交付限制 |
| Git 行为 | 无规定提交阶段 | 上游默认提交修复及最终报告 |
| 外部依赖 | agent-browser 及浏览器环境 | Git、项目服务、浏览器，以及部分配套 CE Skills |
| 最终产物 | 缺陷清单、分步截图、复现视频 | 变更报告、旅程图、矩阵、修复与回归记录、人工待办 |

共同点是“真实操作 + 模型判断 + 文档约束”。两者均检查边界与错误状态、控制台和体验问题，也都采用增量写报告减轻中断损失。它们都不直接证明覆盖率、误报率或可靠性提升了多少。

机制依据：[Vercel 入口](../../../skills-reference/test-dogfood/dogfood/SKILL.md)、[Every 入口](../../../skills-reference/test-dogfood/ce-dogfood/SKILL.md)、[Every 阶段流程](../../../skills-reference/test-dogfood/ce-dogfood/references/phases.md)。

## 2. 用同一功能理解差别

假设改动是“订单提交成功后发送通知邮件”。以下是预期测试方式示例，**不是已经执行的测试结果**。

| 问题 | Vercel 的典型路径 | Every 的典型路径 |
| --- | --- | --- |
| 从哪里开始？ | 打开测试站，沿购物与结算路径探索 | 读订单和通知相关差异，识别受影响流程 |
| 怎样找问题？ | 尝试正常提交、空值、重复点击、刷新；观察订单与页面反馈 | 先列正常、校验失败、权限、重复提交等旅程分支，再逐项验证 |
| 怎样判定邮件正确？ | 若无邮件查看入口或明确要求，不能保证主动检查邮件终态 | 流程要求跟进副作用；有本地邮件替身时核对接收人、内容及链接落点 |
| 发现重复下单怎么办？ | 重试确认，再录像、分步截图，交付缺陷 | 定位根因；小且明确则修复、补回归并重新走场景，复杂则记录决策 |
| 环境收不到真实邮件？ | 记录可观察到的现象，不能由页面成功推断投递成功 | 本次改动涉及且替身无法覆盖的邮件链路标为待人工验证 |

选择建议：只有测试网址、希望交付问题给研发，用 Vercel；有代码、分支和本地环境、希望完成改动验收，用 Every。想做新的测试 Skill，可让同一套“场景—观察—证据—结论”结构服务这两种入口。

## 3. 深读后必须补足的地方

### Vercel：证据规范强，覆盖规划弱

- **问题数量不是覆盖率。** 约 5–10 个问题只是停止启发，可能在外围积累足够缺陷后遗漏关键业务；不应把数量当成功指标。
- **偶发问题容易被遗漏。** 正文要求稳定复现后才算有效问题。新设计应保留偶发观察及尝试次数，单列置信度，避免直接丢弃。
- **视频只证明当时发生过。** 它未记录结构化可执行动作、稳定定位方式、测试数据和断言，不能直接用于 CI 回归。
- **正确性依据可能不足。** 单靠“看起来不对”难区分 Bug、产品取舍和体验建议；需要需求来源或显式预期，尤其是计费、权限和业务状态。

这些判断来自[入口的 Guidance 与 Wrap up](../../../skills-reference/test-dogfood/dogfood/SKILL.md)及[报告模板](../../../skills-reference/test-dogfood/dogfood/templates/dogfood-report-template.md)。分类清单也不能代替专门的压测、安全或无障碍测试工具。

### Every：验收闭环强，基线与状态校验不足

| 观察到的源码事实 | 可能影响 | 新设计应怎样处理 |
| --- | --- | --- |
| Phase 1 示例用 `git diff "$TRUNK...HEAD"` | 未提交改动不在该差异里，浏览器却可能访问包含它们的工作区 | 同时记录 HEAD 与工作区指纹，明确是否纳入脏改动 |
| PR 在 Phase 0 保留身份，但 Phase 1 示例使用仓库默认主线 | 目标为非默认分支的 PR，其实际 base 与测试范围可能不同 | 直接记录并使用该 PR 的 base/head |
| 恢复报告按日期和 branch slug 查找，完成项默认沿用 | 分支新增提交、环境变化后，旧 Pass 可能失效 | 恢复前比对代码、服务和数据版本，只复用仍适用的结果 |
| `Skipped` 与 `Blocked` 都可结束场景 | “流程结束”可能被误读为“可以上线” | 区分运行完成与发布就绪，强制说明跳过理由和关键场景缺口 |
| 回归要求写在文档，报告列有 commit，但缺少统一证据校验程序 | 不能只凭写了“修复前失败、修复后通过”确认真实执行 | 保存两次命令、代码版本、退出码和输出，机器校验关联 |

以上是源码可见的缺口及推论，不代表每次使用必然出错，也不推定宿主不会补齐。[Phase 0、1、5、6 与恢复规则](../../../skills-reference/test-dogfood/ce-dogfood/references/phases.md)是对应依据。

### 两者共同需要的补充

两者都没有附带统一的覆盖账本、证据完整性验证器或量化效果基准。浏览器证据也只能支持所观察的系统部分：界面成功提示不能单独证明数据库或外部服务已正确完成。Every 有意识要求验证副作用，但不附带通用邮件、数据库或队列适配器。

Vercel 会把登录状态保存进输出目录；截图、视频和日志也可能带业务数据。新 Skill 应区分可交付证据与本地会话状态，避免报告发布流程将两者一起打包。这是由产物结构导出的设计要求。

## 4. 哪个更值得作为基础

**轻量可移植入口以 Vercel 为基础，范围规划与修复机制参考 Every。** 保留独立的黑盒模式和改动回归模式；不能让黑盒模式为建立范围而偷偷读源码，也不能让改动回归绕过差异分析直接逛页面。

不建议原样拼接两份指令：是否读源码、是否修复、是否提交、使用哪个浏览器、怎样算结束，都存在不同默认。应先统一输入、状态与证据格式，再把策略作为分支。具体建议见[新 Skill 借鉴建议](05-design-takeaways.md)。
