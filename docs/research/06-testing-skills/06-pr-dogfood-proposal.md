# PR 测试 Skill：初步方案

状态：待评审，尚未实现。日期：2026-11-10。

**给它一个 PR，它先弄清改动影响哪些用户操作，再实际测试；交付“测了什么、发现什么、哪些还没验证”，每个问题附复现证据。** 暂定名：`pr-dogfood`。

## 一次任务怎么跑

| 步骤 | 它做什么 |
| --- | --- |
| 1. 确认测哪份代码 | 读取 PR 的目标分支和最新提交，在独立工作区启动对应服务，记录版本。保留用户现有改动，避免测到另一份代码。 |
| 2. 找出该测什么 | 结合 PR 说明、需求和代码改动，列出受影响的用户操作、容易出错的地方，以及可能被连带影响的功能。预期不清楚的地方单列，不凭代码现状猜“正确答案”。 |
| 3. 生成测试清单 | 先列完整操作过程，再补正常、错误、空值、权限、重复操作等情况。优先测核心流程和容易出问题的分支，并把清单放进报告。 |
| 4. 实际执行 | 用浏览器走完流程；涉及接口或邮件等后续结果时，用项目已有测试方式核实。页面提示成功，不能单独证明后台处理成功。缺少环境的项目标为“未验证”。 |
| 5. 复现并取证 | 发现问题后重新操作确认，记录预期、实际、步骤和截图；多步或时序问题补视频。偶发问题记录尝试次数和出现次数，不直接丢掉，也不冒充稳定复现。 |
| 6. 交付报告 | 分开列出通过、发现问题、未验证和跳过项，说明理由。PR 新增提交后，检查哪些结果失效，再测受影响部分。 |

浏览器优先使用宿主已有且够用的工具，否则用 agent-browser；同一轮使用同一套浏览器。修复权限、Git 提交和推送权限分别遵循用户要求。

## 从两个原版取什么，补什么

| 来源 | 保留的长处 | 要补的地方 |
| --- | --- | --- |
| Every | 从代码改动推导测试范围；沿完整用户流程测试 | 报告绑定实际测试的代码版本，避免新提交后沿用旧结果 |
| Vercel | 发现即记录；截图、视频与复现步骤对应 | 从事先列出的关键测试清单判断进度，不以“凑够几个 Bug”结束 |
| 新增 | 检查证据文件、步骤关联与结果汇总 | 防止报告写了“已验证”，却没有实际执行记录；同时明确记录检查通过不等于业务判断正确 |

## 例子：PR 修改“订单提交”

重点测试：正常下单、参数错误、连续点击两次、无权限操作，以及订单列表和通知是否正确。若连续点击产生两张订单，报告附操作步骤和证据；必要时在改动前版本复查，区分本次引入的问题与原有问题。无法确认归属时如实注明。

最终报告应能直接回答：**这个 PR 影响了哪些操作，哪些测过了，哪里有问题，哪里仍需人确认。** 没有足够覆盖时，不给出无保留的“可以上线”。

## 第一版做到哪

建议先支持 **Web 项目的 PR 测试与报告**：完成范围分析、关键流程验证、复现取证、证据检查和中断后继续。测试过程使用隔离的测试数据；真实支付、对外发消息等操作使用项目替身，无法覆盖就说明缺口。

自动修复放到下一步：用户授权后处理明确的小问题，修复前保留失败证据，修复后重新验证并补回归测试。
