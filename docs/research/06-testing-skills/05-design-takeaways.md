# 新测试 Skill 的借鉴建议

本篇是设计建议，**尚未生成或实现新 Skill**。依据：[核心逻辑](03-dogfood-core-logic.md)、[对比与缺口](04-dogfood-comparison.md)。

**建议目标：让每个测试结论都能追溯到测试范围、实际操作和证据，并能在代码变化后重新验证。** 不以“自动找 Bug”这一已有能力作为唯一创新点。

## 1. 把两组选择分开

| 选择轴 | 模式 | 行为 |
| --- | --- | --- |
| 范围 | explore | 从 URL 和用户任务建立黑盒探索范围，禁止读取被测源码 |
| 范围 | change | 从 PR / 分支 / 工作区差异建立受影响旅程及相邻回归 |
| 操作权限 | report | 只执行获准的测试并交付证据，不改产品代码 |
| 操作权限 | repair | 用户授权后修复明确缺陷并回归；提交权限另行遵循用户要求 |

默认采用 report；创建、修改、删除测试数据也要受目标环境和用户授权约束。借鉴 Every 的大决策转人工机制，避免为了清空失败项擅自改变产品意图。

## 2. 保留的机制

- **Vercel 的即时记录和证据分级：**交互问题保存操作过程与关键步骤，静态问题用截图，发现即落盘。
- **Every 的先旅程后矩阵：**范围 → 入口 → 操作 → 分支 → 后续副作用 → 可验证终态，给场景明确的预期来源。
- **Every 的小修复回归：**行为修复默认需要前失败、后成功的自动化证明；不能自动验证时写明替代检查和限制。
- **Every 的能力探测：**按实际矩阵选择一套浏览器；适配层声明截图、日志、录屏、多身份、网络模拟等能力，缺什么就记录覆盖限制。

## 3. 比上游多做的部分

| 要补的能力 | 最小实现 | 能解决的问题 |
| --- | --- | --- |
| 代码与服务身份 | 记录 base/head、工作区指纹、测试服务来源和数据集版本 | 确保报告描述的代码就是实际被测代码 |
| 结构化场景账本 | 每项记录 ID、需求/变更来源、预期、操作、状态、证据和阻塞原因 | 避免只交缺陷数量，看不到测过与漏测的范围 |
| 证据校验 | 检查文件存在、步骤关联、汇总数量、关键失败证据和回归记录 | 把文档要求变成可执行约束 |
| 恢复失效判断 | 基线变化时重新评估旧结果，不直接继承 Pass | 防止旧报告被误当本次验证 |
| 偶发问题记录 | 分开记录 observed / reproduced / flaky，保存尝试与复现次数 | 同时控制误报与偶发缺陷漏报 |
| 可重跑动作 | 在截图/视频之外保存语义动作、数据前提、预期断言 | 逐步建立可以再次执行的回归资产 |

建议最小账本只保留必要字段：`scenario_id`、`requirement_ref`、`baseline`、`preconditions`、`expected`、`steps`、`status`、`evidence`、`repro_attempts`、`blocked_reason`。保存为 JSON；Markdown 报告从账本生成，减少两份状态漂移。账本校验通过只证明记录一致，不证明业务判断正确。

建议场景状态为 `pending / pass / fail / blocked / skipped`；是否修复独立记为处理记录，最终仍要重新得到 pass。汇总分开输出 **运行是否完成、范围是否充分、是否具备交付条件**，有关键未验证项时不能给出无保留的就绪结论。

## 4. 先做什么

1. **第一版：**Web、两种范围入口、只报告、结构化场景与证据校验、基线记录和恢复检查。不引入完整 CE 技能链。
2. **第二版：**增加修复与前后回归证明；补通用动作回放，处理偶发失败。
3. **后续：**按实际需求接入 API、邮件替身、队列等终态验证，避免先宣称支持所有测试类型。

原始参考继续放在 `skills-reference/test-dogfood/`；新实现另建目录，便于区分上游机制与自有改动。发布前核对 Vercel 的 Apache-2.0、Every 的 MIT 许可原文及必要声明；当前 `UPSTREAM.md` 记录了许可证标识和来源链接，不等于已保存许可全文。

## 5. 怎样证明真的优于原版

用同一测试应用、同一批预埋缺陷、相同模型和预算，对照 Vercel、Every 及新 Skill；同时设置正常流程，避免只找问题不测误报。记录每次代码、数据及环境版本，使用多个独立运行观察波动。

| 指标 | 计算或判定方式 |
| --- | --- |
| 有效发现率 | 经独立审核确认的预埋缺陷发现数 / 本次范围内预埋缺陷数 |
| 确认准确率 | 确认为缺陷的报告数 / 已审核的缺陷报告数；体验建议单列 |
| 复现成功率 | 独立复现成功的问题数 / 已尝试复现的问题数；保留未尝试数 |
| 证据完整率 | 满足对应证据规则的缺陷数 / 报告缺陷数 |
| 回归检出能力 | 将已修复缺陷重新引入后，回归能检出的比例 |
| 恢复正确性 | 人为中断并修改基线后，是否重测失效项、保留有效证据 |
| 成本 | 每次 token、工具调用、耗时，以及每个有效缺陷的成本 |

必须设反例：应用无缺陷时不凑问题数；缺少邮件环境时不报成功；没有视频证据时不编路径；解析器返回码为 0 但含 errors 时不宣称规则已加载。这些是后续验收计划，本轮未执行此对照实验。
