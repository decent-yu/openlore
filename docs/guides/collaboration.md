# 本地开发与云端正式运行

只保留两类环境：**成员各自的本地开发环境，以及团队共用的云端正式环境**。不建设独立测试环境。目前以单人开发为主，后续成员加入时沿用相同方式。

本文约定协作方式和后续 `.env` 配置方向，不代表相关加载或部署自动化已经实现。

## 环境分工

| 项目                     | 成员本地                               | 云端正式环境                                          |
| ------------------------ | -------------------------------------- | ----------------------------------------------------- |
| 用途                     | 修改代码、本地验证                     | 持续采集、运行流水线、归档与群汇报                    |
| 启动                     | `npm run dev`，前后端热更新            | 构建后运行 `node apps/server/dist/cli/index.js serve` |
| 数据库                   | 每人独立 SQLite                        | 单实例控制服务使用自己的 SQLite                       |
| 数据目录                 | 建议仓库内 `.openlore/dev`             | 建议 `/var/lib/openlore`，使用持久磁盘或持久卷        |
| GitHub / Wiki / 通知配置 | 自己的开发配置，按需使用试用仓库与通道 | 正式仓库、Wiki 与通知通道                             |
| AI 执行器                | 本机调用或专门配对本地后端的 Runner    | 独立 Runner 连接正式服务                              |

正式数据库不开放给成员电脑直接连接。成员通过网站/API 使用正式服务，开发时使用各自数据库；不通过 Git、网盘或共享目录同步 SQLite 文件。数据库、材料和凭据均不随代码发布覆盖。

## `.env` 配置方向（待实现）

后续希望在同一份代码的不同部署位置，分别配置仓库根目录 `.env`。不增加独立测试环境，也不使用“开发模式连接正式库”的方式。

本地 `.env` 预期内容：

```dotenv
NODE_ENV=development
HOST=127.0.0.1
PORT=8767
OPENLORE_DATA_DIR=/absolute/path/to/openlore/.openlore/dev
LOG_LEVEL=debug
```

正式 `.env` 预期内容：

```dotenv
NODE_ENV=production
HOST=127.0.0.1
PORT=8767
OPENLORE_DATA_DIR=/var/lib/openlore
OPENLORE_PUBLIC_URL=https://knowledge.example.com
OPENLORE_ADMIN_TOKEN=replace-with-a-random-admin-token
LOG_LEVEL=info
```

路径、域名和令牌按机器实际情况填写。`.env` 放在各自环境中，不提交真实配置；后续实现时提供不含凭据的 `.env.example`。仓库现有忽略规则已排除 `.env`。

`NODE_ENV` 用于声明运行模式；数据目录、监听地址、认证和启动命令仍需明确配置。设置 `NODE_ENV=development` 不意味着自动停用定时任务、屏蔽外部写入或隔离数据。GitHub/Wiki、来源、通知、流水线和汇报方案仍通过各自工作区的网站配置，AI 工作区也由执行器单独配置。

**当前后端没有自动加载 `.env`，也没有根据 `NODE_ENV` 自动切换启动方式或数据目录。**上述仅是后续约定。本次不创建 `.env` 文件、不新增模式开关，也不改启动脚本。

现阶段需要隔离开发数据时，可从仓库根目录使用已有环境变量：

```sh
export OPENLORE_DATA_DIR="$PWD/.openlore/dev"
npm run dev
```

该命令会启动本地服务和调度，开发配置中的外部操作仍可能真实执行。正式服务仍按[部署指引](server-deployment.md)由 shell 或进程管理器传入配置。

## 开发与发布流程

1. 成员获取代码，在本地独立数据目录开发；安装和验证命令见[开发者指引](development.md)。
2. 改动先在本地验证功能，执行与改动相关的测试、类型检查和构建。当前单人开发可自行验收，成员加入后通过 PR 协作审查；不要求先搭建额外平台。
3. 验收后提交代码，再按明确的发布安排更新云端正式服务。环境配置与正式数据留在服务器，发布的是代码或构建产物。
4. 涉及数据库结构时，先备份正式数据，再执行版本对应的初始化/迁移。维护后检查页面、数据与任务状态；正式流水线和群发送按实际需要手动验收。

目前维持单个正式控制服务与 SQLite。CI、自动发布、成员账号权限及独立 Runner 安装包按实际需要再做，不作为当前单人开发的前置条件。Runner 配对与业务数据归属见[系统架构](../architecture/system-architecture.md)。
